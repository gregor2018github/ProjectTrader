# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the Game

```bash
# Install dependencies
pip install -r requirements.txt

# Run the game
python main.py
```

Dependencies: `pygame==2.6.1` and `PyTMX==3.32`. There are no build steps.

## Release (Windows exe)

```bash
py build_tools/Release/build_release.py 0.1.0   # writes release/MerchantsRise-0.1.0-windows.zip
```

A PyInstaller one-folder build (`MerchantsRise.exe` + `_internal/`, own Python, no console) that needs nothing installed, built in its own venv (`build_tools/Release/.venv`) from the git-tracked assets minus what the game never loads (`.xcf`, sketches, raw sounds). Before zipping it runs the exe with `MERCHANTS_RISE_SMOKE_TEST` (handled in `main.py`: straight into a new game, quits after that many seconds, exits 1 on an error). In the exe, `main.py` changes to `_internal/` (where assets, saves and `settings.json` live) and writes a `crash.log` next to the exe on an unhandled error. Pushing a tag `v0.1.0` runs `.github/workflows/release.yml`, which builds the same zip and publishes it as a GitHub release. When the game starts loading a new kind of file or folder, check that the exclusions in `build_release.py` don't drop it; the smoke test only catches what a new game loads in its first seconds.

## Architecture Overview

**Merchant's Rise** is a medieval trading simulation built with Pygame. Games are saved to numbered slots and an autosave (`src/persistence/save_manager.py`, `SAVE_VERSION` 3: a compressed, HMAC-signed blob per slot in `saves/`, with the simulation's own `"sim"` block inside).

### Core Object Graph

`Game` (src/game.py) is the central orchestrator that owns all major objects and runs the main loop. It creates and holds:
- `GameState` — session data and transient UI state (passed everywhere as `game_state`)
- `Depot` — player inventory, money, bookkeeping
- `Player` — player character with map position logic
- `GameMap` — TMX-based tiled map, camera, collision
- `EventHandler` — dispatches pygame events to keyboard/mouse handlers
- `Simulation` (`sim`) — the headless economy, `src/sim/` (see below)
- Lists of `Good` objects — the 30 tradeable goods of `goods.json`, views of the simulation's goods

### Simulation core

`src/sim/` holds the economy's state and rules without pygame (`docs/sim_core.md` has the structure, the tick order, how to add a system and how to run it headless; `docs/p1_living_market.md` is the design of the living market being built in it, on the branch `p1-living-market`; its phases P1.1 to P1.5 are built (demand, production, 30 goods in chains, the full health report, a minimal UI: needs met per class and tier in the town hall's population stats, and yesterday's demand and supply when a good's box in the market view is hovered, `src/ui/market_flows.py`), then a playtest and the merge; `docs/roadmap.md` has the status of every project and the known loose ends). Prices come from supply and demand (`docs/pricing.md`): `price = reference × volume_factor(stock / target_stock) × noise`, the reference being each good's outside price, which walks slowly around its mean, times a running well wish's shock; the target stock is days of the town's demand. Each social class (`ClassState`) has a purse filled by its base income, and a basket of needs in three tiers (`assets/data/needs.json`; above a good's outside price it buys less of it, by an elasticity per tier, and fulfilment still counts against the whole basket) that it buys in hourly slices during market hours (`MARKET_OPEN_HOUR` to `MARKET_CLOSE_HOUR`, `systems/households.py`); merchants import above `reference + transport_cost` and export below `reference - transport_cost` (`market.merchants`); how well each tier was met sets the class's target happiness, which its happiness glides to, and migration follows as before. The player's trades go through `Simulation.trade_with_player` between the slices, so buying up a staple leaves the town short. Workshops (`systems/production.py`, `WorkshopState`) run their building's recipe (`assets/data/recipes.json`, `buildings.json`) for an owner (`OwnerState`; only the town so far, from `assets/data/scenarios/home_town.json`, but no rule reads an owner's kind): their margin at the day's prices sets how hard they run, they hire from one class (when hands are short, shared by workers wanted × margin, `production.share_hands`, a stand-in for P3's wage offers per workshop; a job replaces base income with the class's wage, which rises while hands are short and falls while they are spare, between base income and `wage_cap` in `needs.json`), buy inputs and sell outputs in the same slices, grow after `GROWTH_BUSY_DAYS` busy days within `GROWTH_WINDOW_DAYS` and shrink after `SHRINK_LOSS_DAYS` of losses within `SHRINK_WINDOW_DAYS`; the owner tops them up to working capital and takes the profit, and its `surplus_to` decides the rest (the town: `treasury_with_tribute`, a treasury up to `TREASURY_CAP_DAYS` of its income, the rest paid to the lord out of town). Crowding and migration's floor and ceiling (0.3–1.05) measure against each class's share of the housing. The market place holds no money: the merchants own the stock, every buyer pays them and every seller is paid by them, so the town's money changes by exactly what crosses its border, checked daily as `market_balance` (must be zero). `Simulation` owns the state (`state.py`), one `random.Random(seed)` for all its draws (`rng.py`; no `random.*` calls in `src/sim/`), a `Scheduler` firing the systems on the calendar's ticks (`price_tick`, `hour`, `day`, `week`, `season`, `year`), and an `EventQueue` of what happened (`PriceShockEnded`, `PopulationChanged`, `CapacityChanged`) that the game drains in `Game._handle_sim_events` and shows nothing for yet. `Game.run()` calls `sim.advance_to(game_state.date)` each update; a new game founds the town, establishes the scenario's workshops, and then runs the economy `MARKET_PRESIMULATION_DAYS` ahead (`Simulation.presimulate`). Goods, needs, recipes and building types are defined in `assets/data/` (`goods.json`, `needs.json`, `recipes.json`, `buildings.json`, and `scenarios/`), all loaded and checked by `src/sim/data.py` (`load_definitions`, `load_scenario`). A new game draws a fresh seed (`rng.new_seed()`), shown on the settings' weather page. `Good`, `Town` and `PopulationManager` are pass-through views that keep none of the sim's numbers: a seam, not to be built on. The save's `"sim"` block is `Simulation.to_dict()` with its own `sim_version` (2; version 1 and older saves migrate in `Simulation.load`). `python -m src.sim.run --years 20 --seed 1 --out runs/<name>` writes daily CSVs of the goods, the classes, the workshops and the town plus `meta.json`, `python -m src.sim.health runs/<name>` checks a run (every check of `p1_living_market.md`'s health table, each a `Finding` registered in `health.CHECKS`: fails for broken books, bad numbers, prices pinned at a clamp, hunger, a runaway money supply or population, workshops long in debt; warnings for prices far from outside, poorly supplied or unhappy classes, dead workshops, structural shortages and a town not running slightly short; plus the tradability measure), and `python -m src.sim.sweep` runs 20 seeds × 50 years in parallel, checks each and writes the table over them to `runs/sweep/summary.md` (`runs/` is git-ignored); it takes the town from `Map1.tmx` through `src/sim/scenario/tmx_town.py`, as the core only takes a plain `TownSpec`. Nothing in `src/sim/` may import pygame, `src/ui`, `src/handlers` or `src/models`.

`GameState` (src/game_state.py) is the shared data bus. It does **not** own logic — it stores flags like `left_side_mode`, `right_side_mode`, `info_window`, `warning`, `contract_acquisition`, `time_level`, and `date`. UI components read and write `game_state` directly rather than using signals/callbacks.

### Screen Layout

Total window: **1920×1080**, 16:9 (SCREEN_WIDTH=1810 + SIDEBAR_WIDTH=110). The windowed presets (`RESOLUTION_PRESETS` in `settings_store.py`) are 16:9 too; a size saved before the frame was widened is mapped to the preset in its place (`_OLD_RESOLUTIONS`).

That frame is scaled to fit the screen (`main.py`), with black bars beside it on a wider one. Fullscreen and the smaller windowed presets are `SCALED` displays stretched on the GPU (`_scaled_window()` lowers pygame's minimum window size and turns off SDL's integer scaling through `ctypes`, which pygame 2.6.1 does not offer); only if that fails is the frame smoothscaled on the CPU. The mouse pointer is therefore a system cursor (`src/ui/cursor.py`, `cursor.use("hand" | "quill" | None)`), sized to the scaled frame, not drawn into it, so it moves over the bars too; presses on the bars are dropped.

The content area (1810px wide) is split into two equal **modules** (MODULE_WIDTH = 905px each). Views lay themselves out from the rect they are given; the depot list was laid out for 825px and hands what is beyond that to its detail panel and value column. The top bar shows `TOP_BAR_VISIBLE_COLUMNS` (6) columns of goods. Each side can independently show `'map'`, `'market'`, `'depot'`, or `'building'` (the town plan). When both sides show the same module, it takes the full width. The top bar (60px) and bottom bar (60px) are always visible. The 110px right sidebar holds the navigation pictograms. When what a module shows changes, however it was changed, `ViewTransition` (`src/ui/view_transition.py`, owned by `Game`) rolls a sheet of parchment down over the part that changed, the new view on the sheet behind the roll and the old one (taken from the screen in `begin_frame()`, before it is cleared) below it, with a short `page_turn_*` for one side and the longest one for both.

Rendering layers in the main loop (src/game.py `run()`):
1. Background fill
2. Left/right content modules
3. Persistent UI bars (`draw_layout`, `draw_right_bar`)
4. Overlays in order: debug overlay → menu, time and sound controls → pause overlay → dropdowns → dialogue → info_window → fading menu → contract_acquisition → minigame → warning/message → coin popups → save indicator (the pointer is a system cursor, not drawn into the frame; see above)

### UI Pattern: Modal Overlays

Any modal dialog (quit confirm, house menus, donation menu, contract overview, population stats) is assigned to `game_state.info_window`. The `EventHandler` routes clicks to `game_state.info_window.handle_click()` and keyboard events to `handle_event()` before routing to the rest of the game. Setting `game_state.info_window = None` closes the modal.

Both settings screens (the main menu's, and the in-game `SettingsWindow` in `src/settings.py`, which opens on a chooser between "Chart Colors" and "Controls", plus "Weather" with the debug overlay on: `WeatherDebugPage` in `src/ui/helper_modules/weather_debug.py`, which shows the simulation's seed and starts any spell (`Weather.force`; nothing jumps, the weather develops towards it as in play, and the spell lasts until it has got there), holds it (`Weather.held`, not saved: the spell does not run out and its fog ignores the hour), strikes lightning at once (`Lightning.strike`), soaks or dries the ground, lets everything fall as snow whatever the season (`Weather.always_snow`, not saved) and lays or clears the snow) have a "Controls" button opening `ControlsOverview` (`src/ui/controls_overview.py`), a list of every key and mouse control written out by hand: when a control is added or changed, update its `LEFT_COLUMN` / `RIGHT_COLUMN` too.

`game_state.contract_acquisition` is a special full-screen overlay that **consumes all input** while active.

### Time System

5 speed levels controlled by `game_state.time_level` (1=paused, 3=normal, 5=fastest); at normal speed (`TIME_STEP_LEVEL_3`) a game day takes 8 real minutes. When the map is visible, speed is clamped to 1 or 3. The simulation time (`game_state.date`) advances via `GameState.update()`, at most `MAX_RECULCULATIONS_PER_SEC` (60) times a second, which returns a `TimeChanges` namedtuple (`minute`, `price_tick`, `hour`, `day`, `season`, `year`). Right after it, `sim.advance_to(game_state.date)` lets the simulation's scheduler fire its own systems for every tick passed (`docs/sim_core.md` has the order); the main loop then does the game's own work on the flags:
- **Every price tick** (`PRICE_TICK_MINUTES`, 30 game minutes, so `PRICE_TICKS_PER_DAY` = 48 a day), in the simulation: each good's noise step and one point on the price chart (`Good.price_history_hourly`, the sim's `price_history_ticks`; saves before `SAVE_VERSION` 2 have their hourly charts filled in on loading)
- **Hourly**: in the simulation, a trading slice in market hours (households and workshops buy, workshops make and sell their share of the day's batches, merchants import and export) and happiness gliding to its target; in the game, the crops' stage and the church bell check
- **Daily**: in the simulation, the books close (`market_balance`), the outside prices' walk, the well shock, target stocks, workshops pay wages and settle with their owners (treasury, tribute), the classes' income and plan, migration, the workshops' plans, hiring, wages and capacity; in the game, cost-of-living deduction, loans, overdraft penalty, wealth/stock bookkeeping, licence warnings, the merchant rank
- **Each season**: the reputation fades (`MerchantRank.new_season`)
- **Weekly, yearly**: nothing yet, in the game or the simulation

The calendar is compressed so a game can span generations: a year is four seasons, Spring, Summer, Autumn and Winter, of `DAYS_PER_SEASON` (7) days each, Monday to Sunday, so a game year (28 days) takes almost four real hours at normal speed. `game_state.date` stays an ordinary `datetime` running on from `START_DATE` (its hours, day spans and saves work as ever), but what a day is *called* comes from `src/sim/calendar.py` (also the one place that says when a tick happens, `tick_numbers()`): `game_date()` (year from `CALENDAR_START_YEAR`, season, day of the season, weekday) and the formats `format_long()` ("Wednesday, 3rd of Spring 1500", the top bar), `format_date()` ("3 Spring 1500"), `format_short()` and `format_with_time()`. Never show the clock's own `.month`, `.year`, `.weekday()` or a `strftime` date to the player: it runs about thirteen times slower than the calendar. `TimeChanges` has `season` and `year` (both from the calendar, for ageing once a year later on); durations sold to the player are in seasons (`LICENSE_SEASON_OPTIONS`, `describe_seasons()`: "2 seasons", "1 year"); the depot's periods are `PERIOD_DAYS` (Daily, Seasonal, Yearly, Total). Lent is the winter from its Ash Wednesday (3rd day) to Easter Saturday, Easter Sunday its last day. Balances set per day before the calendar was compressed (licence fees, loan interest, reputation decay) were converted to keep their cost per day.

### Map System

`GameMap` (src/models/map.py) loads a Tiled `.tmx` file via `pytmx`. Map objects are parsed into typed Python objects: `House`, `Town` (extends House — the town hall), `Church`, `Market`, `Tree`. `Town.initialize_population` moves people into the houses (`STARTING_OCCUPANCY` of each one's `Max_inhabitants`) and hands the simulation a `TownSpec` of their capacities; the people then live in the simulation, which `Town` only shows. The `Camera` class handles zoom and panning.

The `Movements` object layer drives map inhabitants: a rectangle named `Sheep` becomes a grazing zone, and each class in `TMXMap.TRADER_TYPES` (a `Trader` subclass) is placed from objects named after its `TILED_PREFIX`: `<prefix>_Market_Stall` (polygon/polyline he walks at work), and optionally `<prefix>_Homeway_Path` plus the points `<prefix>_Homeway_Start` / `<prefix>_Homeway_End` (his way from the stall to his front door). His `MARKET_NAME` links him to his `Market` booth, which is open only while one of its traders is on his stall path: it shuts as soon as the last of them packs up to go home, so each booth (and each good, via `GameState.is_good_tradable`) has slightly different hours. Each trader keeps his own `MarketHours`, drawn nightly from `MARKET_CLOSE_WINDOW`/`MARKET_OPEN_WINDOW`; goods a trader sells beyond his market's name go in `EXTRA_GOODS`. An optional `margin` float property on a polygon, **in tiles**, pulls the walked outline inwards so the NPC keeps clear of its own edges (`inset_polygon` in `src/models/figurines/patrol_path.py`); a margin too large to fit is ignored. Add a trader by drawing his shapes in Tiled, writing a small `Trader` subclass, and adding it to `TRADER_TYPES`. Several traders may name the **same** `TILED_PREFIX`: they then share the one stall and are put on a `StallRota` (`src/models/figurines/humans/npcs/trader.py`), which draws one of them per calendar day — in the dead of night, when yesterday's is home and nobody is out yet. Only the drawn one leaves the house; the rest stay indoors and hidden all day. The alewife shares the vintner's stall, and the tanner and shepherdess share the weaver's. The booth's goods do not change with whoever is minding it.

The `Doors` object layer holds one Tiled **point per front door**, named after the direction a person faces walking out of it (`down`, `up`, `left`, `right`); the Tiled object *id* identifies the door and is what a townsperson remembers. Each `Door` (`src/models/door.py`) keeps three spots on one line: the *threshold* (the Tiled point itself, inside the wall — nobody ever stands there), the *step*, the first spot that many whole tiles out which nothing solid is in (`NavGrid.is_open_at`; it may be hidden behind a neighbour drawn in front of the house, and the grid then opens the shortest way through the hidden cells to the open town, `NavGrid.open_way_out`, so the door is still used), standable, and has a clear line to its own cell centre (a route's first hop is onto the grid, and that hop is validated nowhere else); and between them the *entry*, felt out pixel by pixel as the deepest spot `TMXMap.is_standable()` still allows. A door meeting none of that within `MAX_STEP_TILES` is dropped with a warning naming it, which is a thing to fix in Tiled.

Townsfolk walk entry-to-entry, never onto the point itself — reaching it would put them behind the building, which y-sorts on its own baseline. They come to a **stop at the entry** and only then fade, over `DOORWAY_FADE_SECONDS`, facing the door (`Door.facing_in` / `facing_out`); a doorway fade is not interruptible, not even for a chat.

Fields are objects on the `Fields` layer, rectangles or polygons (`Field`, `src/models/field.py`), whose name picks the crop scattered over them; a name in `BARE_FIELDS` (`Ploughed`) has none (no field uses that now). The Town Plan draws a bare field's furrows upright and names only the sown ones. A crop is a folder `map_sprites/fields/<crop>/` with a `crop.json` listing its growth stages, from the bare field (ground tiles, no sprites) to the ripe crop, at least four, and each stage's variants `<crop>_<stage>_<n>.png` (`crop_sprite_paths()` in `field.py`). Crops and their stages are made in the Sprite Manager's crops area. The crops grow (`CropGrowth`, `src/models/crop_growth.py`, one per sown `Field`): with the seasons of the game calendar: bare (ploughed) through the winter, sown at `FIELD_SOW_DAY` (the 1st of Spring) and growing through the other stages, each an equal part of the time, until it is harvested at `FIELD_HARVEST_DAY` (the end of Autumn) and lies bare again; the stage is worked out from the date alone (`CropGrowth.stage_at`), on starting or loading the game and every game hour (`TMXMap.update_crops`). Each plant is up to half of `FIELD_PLANT_SPREAD_DAYS` ahead of or behind its field, so a field turns over plant by plant within a day or two; a plant at a stage without sprites, the bare field, is not drawn. Plants stand only on the field's inner tiles (all eight neighbours in the field); the edge tiles are its headland, so a field's object in Tiled covers its whole dirt, the ragged edge included. Over the inner tiles lie horizontal furrows (`Field.furrow_overlay`, drawn flat after the ground chunks, half a tile low so the grooves run along the plants' feet, shaded as `plough_field.py` used to bake them): fully shown while the field is bare, wearing away evenly over the sprouting stage, and back in over `FIELD_PLANT_SPREAD_DAYS` around the harvest (`CropGrowth.furrows`); the fade is baked into a copy's pixels in steps of `_FURROW_ALPHA_STEP`, never set as the surface's alpha, which on a per-pixel-alpha surface makes SDL blit it about 8 times slower. The ground under a field is plain dirt. The first `FIELD_STILL_STAGES` stages with sprites (sprouts, young) do not sway in the wind (`Field.still_sprites`). A field's Tiled object may set its own `Sow_day` and `Harvest_day` (days of the year, 0 the 1st of Spring); otherwise both are moved by up to `FIELD_SEASON_JITTER_DAYS`, the same for that field every game (`field_season()`, seeded by its object id), so the fields do not keep step. Nothing of the growth is saved (an older save's `"fields"` is ignored). The plants' places, offsets and variants follow from the object id, so a field looks the same after loading.

Trees are points on the `Trees` object layer at the bottom-left corner of their sprite (`File_name`, `Stem_Position`, `Stem_Thick`, optional `Scale` to draw one smaller or larger; object type `Broadleaf_Tree` or `Pine_Tree`, which the Town Plan draws round or as a conifer); the `Trees 2`…`Trees 7` tile layers only show them in Tiled and are not drawn by the game, which draws only the `Ground*` tile layers. Those it draws from cached chunks (`GroundChunks`, `src/models/ground_chunks.py`, owned by `TMXMap` as `ground_chunks`): `CHUNK_TILES` square, made once per zoom level and kept least-recently-used, in two passes, the layers up to `Ground_Mid` (its water cells left out) under the animated water and the rest over it, that one laid with premultiplied alpha. The ground is not meant to change while playing; if it ever does, the chunks must be dropped. Whatever the view scales or bakes once per zoom level (chunks, tiles, trees, houses, bridges, the mill's blade, the crops at each sway angle, the water's frames and shoreline cut-outs) is made ahead by `MapWarmup` (`src/models/map_warmup.py`, owned by `GameMap` as `warmup`): `prepare()` while the game loads, the starting zoom and the ground around the player, then `step()` each frame for at most `WARMUP_BUDGET_S`, the chunks just outside the view first and then the other zoom levels, nearest first and the hidden Ctrl ones last. Something new the view scales per zoom belongs in its `_zoom_jobs`, or its first frame stutters. The trees, crop sprites and window lights are looked up near the view in `SpatialIndex`es (`src/models/spatial_index.py`; `TMXMap.tree_index`, `crop_index`, `light_index`, `building_light_index`, filed once at load) rather than all checked each frame; something added to the map while playing must be filed there too.

Bridges are rectangles on the `Bridges` object layer (`Bridge`, `src/models/bridge.py`): the whole bridge, railings included. `Deck_top` / `Deck_bottom` (tiles from its top) bound the deck, the full-length band feet may stand in; above and below it are the railings, which block, so the only ways on and off are the ends. Over the deck the water does not count (`TMXMap.check_scenery_collision` tests only the parts of a feet box off every deck), and `NavGrid` opens the deck's cells again. Its sprite (`File_name`, in `map_sprites/houses/`) is one *module*, a span with a post at each end: cropped to what is drawn, scaled to the rectangle's height, and laid side by side (each overlapping the last by its end post, so a join shows one) until the row is at least as long as the rectangle, which then grows to that row, centred. It is drawn flat, after the ground and water and under every walker; an optional `<name>_front.png` on the same canvas, holding only the near railing in the same place, is drawn again over them, y-sorted on the rectangle's bottom. Without a sprite file a plain plank stand-in is drawn. A rectangle taller than it is wide is crossed north to south: its deck is given by `Deck_left` / `Deck_right` (tiles from its left), the railings are left and right of it, and its sprite's modules are drawn upright and stacked downwards. The `River_Bridge` carries the eastern road over the river, the `East_Bridge` the south-east road, and the `West_Bridge` the south-west road over the western stream: `Bridge_01.png` modules, the railing in `Bridge_01_front.png`. The `South_Bridge` takes the south road over the southern river north to south and has no sprite yet, so it shows the stand-in. The Town Plan draws a bridge's deck as planks, and water clicks and thrown stones' ripples keep off it.

Fishing spots are points on the `Fishing` object layer (`FishingSpot`, `src/models/fishing_spot.py`, `TMXMap.fishing_spots`), each in the water just off where the player stands, named as the player reads it (a point not in the water is left out with a message). So far `Wide River`, `River Fork` and `Harbor Pier`. Within `FISHING_REACH_TILES` of one, a click on the water offers "Go Fishing" under the spot's name (`show_water_menu`, which calls `open_fishing`, once a day over all spots). While the day's fishing is still to be done, golden rings spread on the water there (`_draw_fishing_spots` in `map_view.py`); the Town Plan marks explored spots with a fish (`glyphs.fish`), named when hovered, and likewise the chopping stump (`TMXMap.chopping_stump`, the house object named `Stomp`) with a stump and axe (`glyphs.chopping_stump`; `TownPlan._draw_minigame_marks`, `_minigame_mark_at`, a new minigame's place goes there too). All spots play the same pond scene so far.

`NavGrid` (`src/models/navigation.py`) rasterizes house/tree collision rects and the water polygons into one walkable cell per tile, and answers `find_route()` with A* plus line-of-sight smoothing. It also blocks what collision does not: cells where `OCCLUSION_COVER` of a walker's sprite would be hidden behind a building drawn in front of them. Coverage is counted in painted pixels via `pygame.mask`, which is what distinguishes a wall from a fence. Without this, routes run through the band of walkable ground behind tall buildings and walkers simply disappear into them. Only a door's way out may run through such ground (see the doors above; `NavGrid.solid` keeps what collision alone blocks). It is built once, after every blocker has been parsed, and is told the walkers' sprite size so it knows how much of them there is to hide.

`FogOfWar` (`src/models/map_fog.py`, owned by `GameMap` as `map_fog`) remembers which land the player has been near, for the Town Plan only — the map view itself is never fogged. `FOG_CELLS_PER_TILE` cells per tile each remember how well they have been seen (0–255), revealed in a circle of `FOG_REVEAL_RADIUS_TILES` around the player that fades out over `FOG_FADE_TILES`, and never forgotten. It is stored in the save under `"fog"` and restored with `GameMap.restore_map_fog()` once the player is in place; a save without it starts with nothing explored.

`Ambience` (`src/models/ambience.py`, owned by `Game`) keeps the map's ambient loops going, each on a mixer channel reserved in `Game.init_pygame()`, paused while the map is hidden or the game paused (but not while a minigame, which pauses the game, is open): the mill's gears by the distance from its walls (`MILL_VOLUME_BY_DISTANCE`), birdsong in the woods by day (`BIRDS_BY_HOUR`), crickets in nature by night (`CRICKETS_BY_HOUR`), the rivers and the sea by the distance to them (`RIVER_VOLUME_BY_DISTANCE`, `SEA_VOLUME_BY_DISTANCE`), the market crowd by the distance to the nearest *open* booth (`MARKET_VOLUME_BY_DISTANCE`), so it follows the traders' hours, each booth's crowd swelling over `MARKET_SWELL_HOURS` of game time after it opens and dying away as long after it shuts, each market (booths within `MARKET_GROUP_TILES` of each other, `group_markets`) with its own recording (`MARKET_LOOPS`, the biggest market first), the quiet streets where houses stand close together (`STREETS_BY_HOUSES`, booths not counted, so a lone house is silent; it gives way to a market's crowd), and the rain by how hard it rains (`RAIN_VOLUME`; the birds and crickets hush under it). The rain is four recordings, `amb_rain_light_2_loop`, `amb_rain_light_loop`, `amb_rain_medium_loop` and `amb_rain_heavy_loop`, each on its own channel with a volume curve over `Weather.rain` (`RAIN_LAYERS`), so they fade into one another from drizzle to downpour. Every loop glides to its volume (`LOOP_GLIDE_PER_S`) rather than jumping. Owls (`Owls`, `src/models/owls.py`, owned by `Game`) are one-off calls rather than a loop: an `owl_*` once in `OWL_EVERY_HOURS` of game time on the map, the clock running only at night (`OWLS_BY_HOUR`) and as fast as the player stands in a wood (`Ambience.trees` against `FOREST_FULL_COVER`), slowed by rain (`RAIN_HUSHES_OWLS`); each near or far by chance (`OWL_LOUDNESS`) and a little to one side (`OWL_PAN`). Dogs (`Dogs`, `src/models/dogs.py`, owned by `Game`) bark the same way in town (`Ambience.town` against `TOWN_FULL_COVER`), once in `DOG_EVERY_HOURS` (2 to 3 a day), by day and night: a `dog_bark_far_*`, a bout of `DOG_BOUT_BARKS` single `dog_bark_distant_*` barks, or at night (`DOG_CHORUS_HOURS`) now and then the village's dogs (`dogs_far_village_night`). These three, and the coughs, count only game time spent on the map (`MapClock`, `src/models/map_clock.py`). There is no forest, town, river or sea object: a `Cover` works out once, at load, for every tile how much is around it — the stems of the `Trees` for the woods, the buildings (not fences or decorations, `NOT_TOWN_BUILDINGS`) for the town, nature being where the town is not — so a wood grown with the Forest Builder sings by itself; `split_water` tells the sea (open water, with the bay and the harbour) from the rivers (narrow water) by the water tiles' shape, `open_sea` keeps the waves to the sea near the map's edge (`OPEN_SEA_TILES`), so the bay and its harbour are calm, and a `Distance` per kind says how far every tile is from it.

`Weather` (`src/models/weather.py`, owned by `Game`, saved under `"weather"`) goes through spells of `WEATHER_SPELLS` in game time (clear and overcast, showers of drizzle, rain (3 to 24 hours, half of them under 5: a spell's `hours` may give a median length, the long ones then growing rarer), sometimes a downpour, now and then a thunderstorm (`storm`), and clearing, 1 to 2 a week, and mist, now and then thickening into fog, after a clear spell or a shower; each spell lasts some hours and is followed by one drawn from its `next` weights); the seasons bend that (`WEATHER_BY_SEASON`: per season, factors on the `next` weights and on a kind's `hours`, by the season a spell starts in), and on all fog (`"fog"`, the spells' and the wet ground's): Summer has less rain, no mist or fog at all and the only thunderstorms (most of its showers end in one, about one storm every other summer), Autumn twice the rain and three times the fog, Spring and Winter as `WEATHER_SPELLS` has it but without storms; a spell forced from the debug page keeps its fog whatever the season; its `rain`, `clouds` and `wind` glide towards the spell's at `WEATHER_GLIDE_PER_HOUR`, so showers set in and pass off; the rain waits for its clouds (`Weather.rain_ceiling()`: none below `RAIN_FROM_CLOUDS` of cover, the spell's rain once its clouds are there), so the sky clouds over before it rains and the rain eases off before it clears. Its `fog` (0 to 1) glides slower (`FOG_GLIDE_PER_HOUR`) towards the spell's `fog` or the wet ground's own mist once the rain has stopped (`FOG_FROM_WETNESS`), whichever is more, times what the hour allows (`FOG_BY_HOUR`: thick at night and before dawn, mostly burnt off by noon). `Fog` (`src/models/fog.py`, owned by `GameMap` as `fog`, advanced only while the map runs; not the fog of war, which is `map_fog`) draws it in layers after the lighting and before the rain: an even veil, banks from three layers of tiling noise drifting at their own speeds with the wind (soft round bumps, not a grid, since the banks' threshold would show a grid's creases), gathering over water, thinner round the player (`FOG_CLEAR_RADIUS_TILES`), loose wisps (`FOG_WISPS_PER_MEGAPIXEL`) and a glow round every lit window. Veil, banks and clearing are worked out in gray at 2 pixels a tile and smoothed up as a multiply and an add, 15 times a second or when the camera crosses one of those pixels; its colour follows the scene's light. Clouds dim the map through the day/night overlay (`daylight.overcast()`, `CLOUD_TINT`, less so at night). A thunderstorm's `storm` level (only the `storm` spell has one; it glides like the clouds and is saved) dims it further (`STORM_TINT`) and brings `Lightning` (`src/models/lightning.py`, owned by `Game`, real seconds while the map runs): strikes every `LIGHTNING_EVERY_S` at full storm, none below `LIGHTNING_FROM_STORM`, each flickering once to three times (`FLICKERS`; `map_view` adds the flash over the map, up to `LIGHTNING_FLASH_ADD`) and mostly followed after `THUNDER_DELAY_S` by one of the `thunder_*` sounds, the later the softer (`THUNDER_VOLUME`), never the same twice running. `Rainfall` (`src/models/rain.py`, owned by `GameMap` as `rain`, only advanced while the map runs) keeps the drops in world space around the view, `RAIN_DROPS_PER_MEGAPIXEL` of them at full rain, each landing as a splash, or as a ring on water. The splashes and rings on the ground are drawn on the ground (`Rainfall.draw_ground`, after the puddles and before the render queue), so whoever and whatever stands over them hides them and the lighting darkens them; the falling drops and the splashes on roofs are drawn over everything after the lighting, dimmed by it, in one `blits()` call. Drops also burst faintly off the tops of people and animals out of doors (`FIGURE_SPLASHES_PER_PX_S` per pixel of their width, `Rainfall.figure_splash_entries`, put in the render queue just over each figure, the top of its sprite looked up only in the columns hit). On a building a drop only splashes inside a roof: polygons on the `Roofs` object layer, named after their building (`TMXMap.roofs`, `src/models/roofs.py`, which files every building's painted pixels and the roofs by tile); elsewhere on a building's sprite it ends unseen. A polygon there of Tiled type `Hole` is where a roof is open (a courtyard): it cuts the roofs named after the same building that it overlaps (`match_holes`), for the rain and the snow caps alike. A new building needs its roof drawn (`place_building.py roof`, see the place-building skill). The ground's `wetness` (in `Weather`, rising with rain by `PUDDLE_FILL_PER_HOUR`, drying by `PUDDLE_DRY_PER_HOUR`) drives `Puddles` (`src/models/puddles.py`, owned by `GameMap` as `puddles`): each wet spell, once the ground was dry, scatters new ones over a few updates (at most `PLACE_BUDGET_S` of each), mostly on road and paving (`PUDDLE_PATH_TILES_EACH`; the tiles come from `TownPlan.trodden_tiles()`, the rest get `PUDDLE_OFF_PATH_SHARE`), never touching a building's or tree's collision box or painted pixels (`pygame.mask`), water, bridges or fields. Each shows from its own wetness threshold and grows to full size; some are longer (`PUDDLE_WIDE_SHARE`, `PUDDLE_WIDE_TILES`, never taller). It is drawn flat on the ground before the render queue: a multiply (so the ground shows through), the sky, then whatever in the queue stands behind or in it, mirrored about its base line and cut to the water (a mirrored building's lit windows too, each light filed once under the building it is on, as a glow `Puddles.draw` returns for `_apply_lighting` to let through), then a thin pale rim; raindrops ring on it, and so does anyone walking through it (`Puddles.update_walkers()`, each `RIPPLE_STEP_PX` walked in the water a step's rings, cut to it, a few droplets thrown up, and the reflection shaken sideways in bands while they last). Under the puddles, `WetGround` (`src/models/wet_ground.py`, owned by `GameMap` as `wet_ground`) darkens the ground by how wet it looks (`wet_level()`: the wetness plus a little of the rain), with a tint per kind of ground (`WET_TINTS`, from `TownPlan.ground_masks()`), unevenly: each spot darkens at its own threshold (smooth noise), lowered round every puddle, so the ground wets and dries in blotches and each puddle sits in a damp patch. It is kept at 4 pixels a tile and the view's part smoothed up in one piece, made again only when the camera has moved a quarter tile or the wetness changed. In Winter the rain falls as snow: `Weather` splits what the spell lets fall into `rain` and `snow` by the share the day of the year turns to snow (`snow_share_at()`, `SNOW_BY_DAY_OF_YEAR`: sleet on the first and last days of Winter), so everything that reads `rain` (the rain's drops and sounds, the wet ground, the puddles) simply stops in the snow, which is silent. Snowfall builds up `snow_cover` (`SNOW_FILL_PER_HOUR`, saved), which lies as long as it is cold enough to snow and thaws after (`SNOW_MELT_PER_HOUR`, faster in rain), the meltwater wetting the ground (`SNOW_MELT_WETS`), so a thaw leaves puddles; the puddles go by `Weather.puddle_level`, the wetness the snow does not hide. `Snowfall` (`src/models/snow.py`, owned by `GameMap` as `snow`) draws the flakes like the rain, in world space, slow, swaying and carried by the wind (`SNOW_FLAKES_PER_MEGAPIXEL` at full snow), the near ones settling and fading where they land (on the ground under everyone, on roofs over them). `SnowCover` (`src/models/snow_cover.py`, `GameMap.snow_cover`) whitens the ground after the wet ground, built like `WetGround`: patches at their own depth of cover (noise), thinner on the roads, paving and forest floor, none on water. `RoofSnow` (`src/models/roof_snow.py`, `TMXMap.roof_snow`) puts a snow cap over every building's `Roofs` polygons, made from its sprite and queued just over it, white from `SNOW_ROOFS_FROM`. Trees and crops get no snow yet. With the debug overlay on, F9 starts the next kind of weather, and the settings have a weather page (see the UI section).

The length of the day follows the seasons through the *sun hour* (`src/models/daylight.py`, `sun_hour()`): everything that goes by daylight is set out for a day of Spring or Autumn (full daylight 8:00 to 17:00, night 21:00 to 4:00), and `sun_hour()` turns the clock into the hour of such a day that looks the same. At midsummer the dawn comes `DAYLIGHT_DAWN_SHIFT_HOURS` earlier and the dusk `DAYLIGHT_DUSK_SHIFT_HOURS` later, at midwinter the other way round, by degrees over the year (a cosine of the calendar day, so a season's turn shows no jump); in Autumn and Winter the dawns and dusks also last up to `DAYLIGHT_TWILIGHT_STRETCH` longer, most where Autumn turns to Winter (`twilight_stretch()`). The light also has a mood by season (`season_tint()`, `SEASON_LIGHT_TINT`, multiplied into the map's light at every hour, blended between the seasons' middles): clear in Spring and Summer, warm and reddish in Autumn, cold and bluish in Winter; so in Autumn and Winter the lighting overlay is drawn by day too, as it is at night. The map's light (`ambient_light()` in `daylight.py`, its keyframes `AMBIENT_KEYFRAMES`; the minigames played outside are lit by it too, through `Outdoors` in `src/models/minigames/outdoors.py`: the sky at the hour with the sun or the moon (its phase once a season) and the stars, the light dimmed by clouds and storm like the map's and lifted a little at night, lamps of the scene's own lit after dusk, the game's rain, snow (and the snow lying), fog, clouds and lightning with thunder; the woodhacking's scene is the first to use it), window and building lights, chimney smoke, the knock's night check, birds, crickets, owls, the dogs' night chorus and `FOG_BY_HOUR` go by it; what goes by the clock (markets, townsfolk going out, the church bell) does not. Something new that should follow the daylight reads `sun_hour(date)` instead of `date.hour`.

`StreetLife` (`src/models/town_life.py`) keeps `STROLLERS_BY_DAY` / `STROLLERS_BY_NIGHT` townsfolk out at a time, fewer while it rains (`STROLLERS_IN_RAIN_*`, from `Weather.rain` reaching `STROLL_RAIN_FROM`; those out finish their walk). A `Townsperson` (`src/models/figurines/humans/npcs/townsperson.py`) steps out of their door fading in, walks a cached door-to-door route — stopping to look at something now and then — and fades out into the door they arrive at, which becomes their home for the next outing. Nobody is out twice, because there is only one object per person. There is no `Townsperson` subclass per person: `discover_townsfolk()` creates one per sprite folder holding an `npc.json`, so adding a townsperson is adding the folder. Their positions are session state, not saved. `StreetLife.update()` only directs; the townsfolk themselves are walked by `update_npcs()` like any other NPC. A route not walked before is worked out over several frames (`NavGrid.route_steps()`, a generator yielding every `SEARCH_CELLS_PER_STEP` cells searched or `SIGHT_SAMPLES_PER_STEP` sight-line samples; `find_route()` runs it in one go), at most `ROUTE_BUDGET_S` of each, while whoever is going out waits indoors: done in one frame, a long one took 20 to 40 ms here and far longer on a slow PC.

Each door is handed to the building whose collision rect its point sits in (`TMXMap._attach_door_to_house`), which is what connects a knock to the people behind it. Knocking on a house somebody is home in has a `KNOCK_ANSWER_CHANCE` of being answered: `StreetLife.answer_knock()` picks one of its residents, who opens the door, steps onto the doorstep, stands there `KNOCK_ANSWER_SECONDS` and goes back in. Talking to them holds that wait for as long as the bubble is open.

Every NPC has a `GENDER` (`"male"` or `"female"`, `NPC.GENDER`): a townsperson's comes from the `"gender"` in their `npc.json`, a trader's is a class attribute (the alewife, farmer, herbalist, shepherdess and weaver are women). `Coughs` (`src/models/coughs.py`, owned by `Game`) uses it: every `COUGH_EVERY_HOURS` of game time spent on the map (1 to 2 a day; time off the map or a jump of over an hour does not count) a random NPC out of doors within `COUGH_MAX_DISTANCE` of the player coughs a `cough_man_*` or `cough_woman_*`, softer the farther off (`COUGH_FALLOFF`); with nobody near it tries again after `COUGH_RETRY_HOURS`.

Clicking a figurine opens its menu (`src/ui/helper_modules/figurine_click_menu.py`). "Chat" says a line of their class's sentence file in `assets/texts/NPCs/` (plus the traders' file for a trader), or with a chance of `RUMOUR_CHANCE` (`sentences.py`) one of `sentences_generic_rumours.txt` allowed to them: hints at how the game works, in the townsfolk's words, so when a mechanic changes, check they still hold. A rumour names who may say it, as `• [Poor, Commons, Traders] The sentence.` (social classes, and `Traders` for anyone who trades, whatever their class; without brackets anyone may). In any of these files, a line about the speaker's marriage uses a placeholder of `SPOUSE_WORDS` (`sentences.py`), as `my {spouse}`, filled in by `NPC.GENDER`: a man has a wife, a woman a husband. Anyone whose `SOCIAL_CLASS` is `"Poor"` is also offered a coin: `ALMS_COIN` is booked as a donation under `ALMS_CATEGORY` ("Alms", a bookkeeping category of its own), with the donation feedback (`on_money_donated`, which for a gift of one coin plays `coin_flip` or a `coin_single` variant, by even odds, instead of the falling coins; church and town donations use it too), and the speech bubble then opens with their thanks, a line of `assets/texts/NPCs/sentences_thanks_alms.txt` (`NPC.thanks_line`), a `•` bullet per sentence like the other sentence files.

### Town Plan

The `'building'` view (sidebar tooltip "Town Map"; the `'map'` view's is "Explore") shows the whole map as an old paper plan of the town, in its own package `src/ui/layout_modules/town_plan/`. `TownPlan` (`view.py`) is owned by `Game`; it is told `begin_frame()` each frame and only takes input (wheel zooms towards the cursor through `ZOOM_LEVELS`, dragging pans) while it was drawn, routed from `EventHandler` ahead of the usual click handling. The legend keeps the bottom-right corner unless the player's mark comes near it; then it moves to the first of bottom left, under the compass or under the title that is clear of the mark (`_place_legend`, with a gap between `LEGEND_STAY_CLEAR` and `LEGEND_MOVE_CLEAR` so it doesn't hop back and forth). The player can also drag it anywhere on the sheet, and it goes back to its corner the next time the plan is opened. Nothing on it is drawn by hand: `terrain.py` averages the `Ground*` tile layers down and picks water, sand, road, cobbles and forest floor out by colour (`GROUND_*` in `style.py`) into `pygame.Mask`s, and `landmarks.py` turns the `House` objects into roofs, stalls, fences and named places, and finds where the bay's and the wood's names fit. `engraving.py` inks that once per zoom level, at the level's own resolution (so lines stay fine); `TownPlan.prepare()` builds all of it while the game loads, so opening or zooming the plan never stalls; what changes while playing — the player's mark, the map camera's frame, packed-up stalls, owned warehouses, names, the hover tooltip — is drawn on top each frame (`ornaments.py`), on parchment whose grain is pinned to the land, so it moves when dragged. Only explored land is charted: `TownPlan._cover_unexplored()` lays the blank paper (a shade darker, `UNCHARTED_TINT`) over the rest through the fog's veil, and unexplored names and buildings are neither labelled nor hoverable. With the debug overlay on (`show_map_debug`), a radio switch under the title panel ("Explored land only" / "Everything", `TownPlan.reveal_all`, not saved) lifts that cover to show the whole map. A new building, road or patch of water in Tiled shows up on the plan by itself; a new *kind* of building needs a case in `landmarks._kind`. Colours, fonts and names are in `style.py`.

That parchment is `src/ui/paper.py`'s `draw_paper()`, shared with the loading screen and the market and depot chart backgrounds: a seamless grain tile laid from an anchor point plus browned edges for the rect, made from any base colour (`PARCHMENT*` in `colors.py`; the charts use `SANDY_BROWN`). `PAPER_GRAIN` sets how strongly it shows.

### Trading System

`Depot` (src/models/depot.py) manages money, `good_stock` (Dict[str, int]), and FIFO `purchase_history` for profit tracking. Trading licences are a guild's: each good's `license` in `goods.json` names the licence it is traded under (its own, or its chain's head: Flour and Bread under Wheat, Tools under Iron), and `Depot.trading_licenses` is keyed by licence (`Depot.license_of`, `has_license(good)`); each expires after a duration, its fee per season being the head good's `license_fee`. Every list of goods (the depot's accounts, quick-trade quantities, the dropdowns, the licence overview, the booths' extra goods via `sold_at` and `Market.SOLD_AT`) comes from `goods.json`; `constants.py` keeps no per-good lists. The top bar shows the goods pinned with a right-click on a good's box in the market view (`GameState.pinned_goods`, saved; a new game pins the first `TOP_BAR_DEFAULT_PINS`; a folded corner on its market box, `src/ui/pin_marker.py`, marks them) and those held, in goods.json order; past `TOP_BAR_VISIBLE_COLUMNS` columns its arrows scroll it. A good's quick-trade quantity starts at about `QUICK_TRADE_LOT_VALUE` worth (`quick_trade_quantity()` in `game_state.py`). `good_stock` is the total; where it lies is kept in storage **slots**, each holding up to its size of one good only, so the room left in a part-filled slot is lost to every other good. The starting storage (no building) has `STARTING_STORAGE_SLOTS` of `SLOT_SIZE` (`Depot.starting_slots`); each warehouse declares its own in Tiled (`Buy_slots`, `Buy_slot_size`) and, once owned, keeps them in its `properties["warehouses"]` entry (`"slots"`, `"slot_size"`). `buy` checks `room_for()` and tops up slots already holding the good before taking empty ones, going through the storages in `Depot.storage_order`, the player's priority list (keys `START` and the warehouses' Tiled ids; the starting storage first and warehouses as bought, until reordered with `move_in_priority`); `sell` goes through it from the other end, least-filled slots first. Filters steer where goods may go: a warehouse accepts all goods or some (its entry's `"accepts"`, `set_accepted_goods`), and a slot may be reserved for one good (its `"reserved"`, `set_slot_reservation`), which it alone then takes whatever the warehouse accepts (`Depot.slot_takes`); they never throw out what is already stored. A purchase only the filters stop is refused with its own warning (`room_for(..., filtered=False)` tells it apart); `settle_storage()` repacks them after loading if they disagree with `good_stock`. The player's pack (`Depot.pack_slots`, `PACK_SLOTS` of `PACK_SLOT_SIZE`) is slots too, its goods part of `good_stock`: purchases never go into it, sales take from it last, and `total_capacity()` counts it. An owned warehouse's house menu has "Manage Inventory", which opens `WarehouseInventory` (`src/ui/helper_modules/warehouse_inventory.py`): the warehouse's slots over the hands', a click moving a slot's goods across (`carry_from_warehouse`, `store_in_warehouse`, which follows the filters too), a right-click one unit. Over them is a settings strip: the priority list with buttons moving this warehouse earlier or later, and the goods it accepts; the funnel in a slot's corner reserves it. Goods are picked in a `GoodsPicker` (`goods_picker.py`). `PlayerInventory` (`player_inventory.py`, opened with I or from the menu of a click on the player's figure) only shows the hands. Both are an `InventoryWindow` (`inventory_window.py`) of `SlotSection`s, drawn into a cached panel redrawn only when the slots or the footer change. The `Good` (src/models/good.py) is a view of the simulation's `GoodState` (current price, market quantity, per-tick/daily price history) plus its chart colour and visibility. The church's house menu also has "Donate Goods" (`FeastMenu`, `src/ui/helper_modules/feast_menu.py`): the meals in `CHURCH_FEASTS`, each a set of goods given out of `good_stock` by `Depot.donate_goods()`, which takes them like a sale (slots, oldest purchases first) but with no trade cycle, and books their market price on the day as a donation under `CHURCH_FEAST_CATEGORY` (and in `Statistics.goods_donated` / `goods_donated_value`); money does not change, and if any good falls short nothing is taken and a warning names what is missing. How prices are calculated, and where each part of that lives, is in `docs/pricing.md`: update it when the price model changes.

### Merchant Rank

`MerchantRank` (`src/models/merchant_rank.py`, owned by `Game` as `merchant_rank`, saved under `"merchant_rank"`) holds the player's title on the ladder `MERCHANT_RANKS` in `constants.py`, Peddler to Patrician. Each rank asks for four things at once: net wealth (`Depot.net_wealth()`, property included, loans taken off), property value (buildings at their buy price), lifetime trade volume (`Depot.trade_volume()`, goods bought plus sold) and reputation (`Player.reputation`). Rising is checked every game update, paused or not (`check_rise`): the moment all four allow it the player rises to the highest rank they can, and `RankUpWindow` (`src/ui/helper_modules/rank_up_window.py`) announces it on a certificate-like sheet: the numeral in a wreath, the ladder, what it opens, the road to the next rank, a line per rank in `RANK_WORDS` (a rank with none just leaves it out), "Rank Restored" for one held before. It takes no input for `INPUT_DELAY_S`, so a click meant for the market does not close it. Falling is judged at midnight (`daily_check`): when the rank held stops being met, a warning starts `RANK_GRACE_DAYS` of grace, after which they fall back one rank (and get a new grace period if that one is unmet too). The rank shows at the right of the top bar, red while slipping; clicking it, or "Merchant Rank" in the Guildhall's house menu, opens `RankWindow` (`src/ui/helper_modules/rank_window.py`), the whole ladder against what the player has. Rank changes go to the ledger under `RANK`. Rises and warnings wait in `Game._pending_notices`, shown one at a time by `Game._show_next_notice`, which pauses the game and holds them back while a dialog, a minigame or the contract view is open. What a rank opens is in `RANK_UNLOCKS` (rank name per unlock, read with `has_unlocked()`) and follows the *highest* rank ever reached, so it is never taken away; so far only `buy_buildings` (Hawker), checked in the buy-building dialog, which is why Hawker asks for no property. Bonuses that follow the rank held are not decided yet. Reputation comes only from gifts so far (church, town, alms, and goods given to the church for a meal for the poor: `record_gift()` after the donation is booked): a season's gifts together earn `DONATION_REPUTATION_SCALE * ln(1 + given / W)`, W being what the giver was worth before them, so each coin earns less than the last and the rich must give far more; it fades by `REPUTATION_SEASONAL_DECAY` at the start of each season.

"Records" in the Guildhall's house menu opens `RecordsWindow` (`src/ui/helper_modules/records_window.py`), the player's successes, so far the minigames', a tabbed page each, on a sheet in the style of the minigames' how-to pages and certificate (`draw_paper`, `draw_flourish`, `draw_divider`, `draw_laurel`, and `tutorial_sheet`'s `draw_tab`, `plaque` and colours), each page drawn once and kept while the window is open. Fishing: the best day's fishing, and a card for every kind of fish but the minnows with its portrait, name, how many were landed, their weight together and the biggest one (`Statistics.fish_tally`, `fishing_records`, filled by `Statistics.record_fish`); a kind not caught yet is grey with a question mark for its name. Woodhacking: the top `WOODHACKING_TOP_SCORES` scores with their calendar dates, hovering one shows its session's best streak, perfect hits (swings perfect on both gauges) and blocks chopped (logs split), and beside them the bests and totals over all sessions (`Statistics.woodhacking_scores`, `woodhacking_bests`, filled by `Statistics.record_woodhacking` when a session is finished; one left early counts for nothing). What was not tracked yet shows as `-`: an older save keeps its high score as an entry with nothing else known, and its bests start with its first new session. A fish's weight follows from its kind and length, `Species.kg(cm)` (`Species.plumpness` × length cubed), and `Fish.kg`; it pays nothing yet, coins still go by length (`fish_coins`). Saves from before the tally count each kind with a record as one fish of that weight.

### Taverns

A building with a `Tavern` property in Tiled (`low`, `middle` or `high`, kept as `House.tavern_class`) is a tavern; its house menu has "Daily Menu", which opens `TavernMenuWindow` (`src/ui/helper_modules/tavern_menu_window.py`). The dishes are period ones in `assets/texts/taverns/dishes.csv` (dish, class, course, meat, price in coins, description; the menu shows the price); `daily_menu()` in `src/models/tavern_menu.py` draws `MENU_COURSES` of each course from the tavern's class, the same all day (seeded by the date and the tavern) and different from tavern to tavern, with no meat on fast days (Fridays and Lent, `calendar.is_fast_day` in `src/sim/calendar.py`). So far there are two: the Grey Griffin Inn on the market square (`middle`) and The Golden Sheaf north of it (`low`).

Everything else lives in one self-contained tool, `Sprite_Manager/Sprite_Manager.py` (the Sprite Manager). It opens, behind a splash of three random sprites from three random areas, fanned like cards while it reads the sprites (`splash.py`), on a start page (`view_home.py`) showing every sprite at a glance — how many, new and redone today by their file dates (`daily_progress.py`), answers waiting — with a big card each, three to a row, into the humans, the plants, the buildings, the crops, the animals and the menu sprites (click, or 1 to 6; Escape or "Start page" there comes back). The menu sprites area (`goods.py`, `view_goods.py`) collects the goods' pictures: for every good of `goods.json` its `<good>_30.png`, its 1024px painting `<good>_full.jpeg`, the cut-out `<good>_icon.png`, its licence picture `contracts/<good>.png` (the good toned sepia, made with the others from its painting; the game shows a licence's head's) and the signed licence's snapshot the game writes itself (a licence's head only), each shown as there, a placeholder (the chart-coloured discs with initials of the goods added in P1.3) or missing. "Make its picture" sketches a good on a 2x2 sheet beside three random goods that have paintings, cut out onto white for the style (`goods_sheets.py`, `view_good_design.py`; what it is comes from `build_tools/output/goods/<good>/description.txt`), sent like the other sketches; accepting an answer (`view_good_answers.py`) writes its `_full.jpeg`, `_icon.png`, `_30.png` and licence picture, keeping the old ones in that folder's `replaced/`. The animals area (`animals.py`, `animal_sheets.py`, `view_animals.py`, `view_animal.py`, `view_animal_answers.py`) lists the folders under `figurines/animals/` and adds animals; an animal's frames face left (standing, `move1`–`4`, `eat1`–`2`), accepting one also saves its mirror image as `<animal>_right_<frame>.png`, and the sheep is its pose guide as the chibi is the humans': a frame is drawn on a 2x2 sheet in the sheep's pose, a new animal's standing sprite beside the sheep standing. The crops area (`crops.py`, `view_crops.py`, `view_crop.py`, `view_crop_design.py`, `view_crop_answers.py`) adds crops and makes their growth stages like walk frames: on a crop's screen the stages (added after the chosen one or taken out, with a title, description and height for the prompt), the chosen stage's variants, and the chosen variant growing stage by stage at one scale. Each stage sprite is drawn from a reference sprite and a sketch, like a new plant (`crop_sheets.py`): Enter or a click on its sheet opens the sketch screen, the plants' and buildings' `SketchView` (`view_sprite_design.py`) with the stage's dashed red height line and grey ground line drawn over the red frame as help only, never in the image sent. There the reference is picked, which picks the prompt: another stage of the crop to grow it from (the ripe plant for a smaller one), another variant of the stage for a variation, or, for a crop with no sprite yet, another crop's ripe one for the style (default `Crop.reference_for()`). Each reference keeps its own sketch in `build_tools/output/crops/<crop>/sketches/`; a variant not sketched cannot be sent. It adds people (gender and a name from `medieval_names.py`, or a trade; townsfolk get `npcs/<class>_<name>/` with an `npc.json`) and makes their first front sprite from a description, and can redo the front sprite of anyone who has one. It makes NPC walk frames (`<prefix>_<direction>_move<n>.png`) and standing sprites from the base chibi's strips in `base_Chibi/`, and the player's frames: his run is `player_<direction>_move<n>.png` (in the game he only runs), his walk `player_<direction>_walk<n>.png`, not loaded by the game yet. Per frame it builds a 2x2 sheet with a see-through ghost of the pose in the target cell (with "Head: Locked" the figure's own head is put in place of the ghost's, where its standing sprite faces the frame's way; "Sheet: Two cells, red ghost" (L) sends only the figure beside the pose as a red ghost instead, with its own prompt, and each answer records its layout so `extraction.py` splits it right), handed to Gemini either through the API or by copy and paste via the web view (`win_clipboard.py`), or with "Send in browser" (Ctrl+W): `web_bridge.py` serves it on 127.0.0.1:47613 to the userscript `gemini_bridge.user.js` (Violentmonkey/Tampermonkey, installed from that address), which opens a new chat in the Gemini tab (opened in the Firefox profile `FIREFOX_PROFILE`, "ProjectTrader", where the userscript is installed), sets the thinking level to High and sends image and prompt, then waits (up to ten minutes) for the answer's image and clicks its "Download full size"; the tool picks the new file out of the Downloads folder, books it on the sheet it was sent for as if opened, and plays a small chime made from sine waves (`chime.py`) ("Send missing in browser", Ctrl+Shift+W, sends every frame of the direction not done yet that way, one after another, and plays a full chime when all are through, stopping at a sheet that fails); a sheet that does not come through plays a falling chime; its selectors are what to fix when Gemini's page changes. Every answer is kept in `build_tools/output/<npc>/` and listed in a `review.json` (`pose_review.py`), to be accepted into the sprite folder or marked as not good enough; `extraction.py` cuts the sprite out and scales it. "Even out colours" (`even_colours.py`, needs numpy) pulls a direction's frames onto its standing sprite's colours, material by material, so the walk does not flicker; the old frames are backed up and one click undoes it. The plants and the buildings areas (Tab goes round all three) show the map sprites, by kind (a building some object on `Map1.tmx` names in its `File_name` is labelled "in game"). Both are a `Domain` of `sprite_library.py` (`plants.py`, `buildings.py`: kinds, proposals, prompt, Tiled hints); which kind each sprite is lives in `plant_catalog.json` / `building_catalog.json` (right-click to change), and the small plants, which exist only inside `non_collision_deco.png`, are cut out of it on the fly. Clicking a sprite starts a new one with it as the example: the user sketches the shape in the red frame beside it (under it, for a wide one) in flat colours (brush, straight-line and fill tools; the colours used last are quick picks, kept per domain in `recent_colours.json`), picks type and an optional subcategory, and the split image goes to Gemini like the humans' sheets. Accepting saves a single sprite (`trees/Tree_<n>.png`, `houses/House_<n>.png`, ...) and stamps it into the first free tile-aligned place of `Trees.png`, `non_collision_deco.png` or `Houses.png` for Tiled, after backing the PNG up (the `.xcf` sources are not updated); the status line gives the Tiled properties for its object (a tree's stem, a building's size and collision box, a bridge's `Bridges` rectangle and deck guess). A kind may add rules to the prompt (`Kind.prompt_notes`, as the bridges do). Floor plates (the market square's paving, `floor_plates/Floor_<n>.png`) are a buildings kind whose collection is `assets/tiles/ground_tiles.png`: a new one is stamped there and painted onto `Ground_High` from the `ground_tiles` tileset; the single sprite is only the tool's example and is not loaded by the game. A bridge's near railing is cut out as its `_front.png` by `bridge_front.py`: `prepare` writes the bridge on white plus a prompt asking Gemini to paint all else magenta, `cut` takes the answer as a mask over the bridge's own pixels. The main script only holds the window, main loop and shared state; each screen is a `View` subclass (`view_*.py`) and the non-UI parts live in their own modules — its docstring maps them. Prompts for hand use live in `sprite_prompts/`. The API needs `pip install -r build_tools/requirements.txt` and a key: `GEMINI_API_KEY` in the environment or in `.env`, or the raw key in `trade_envi/GEMINI_API_KEY.txt` (the venv is git-ignored).
