# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Running the Game

```bash
# Install dependencies
pip install -r requirements.txt

# Run the game
python main.py
```

Dependencies: `pygame==2.6.1` and `PyTMX==3.32`. There are no build steps.

## Release (Windows exe)

```bash
py build_tools/Release/build_release.py 0.1.0   # writes release/MerchantsRise-0.1.0-windows.zip
```

A PyInstaller one-folder build (`MerchantsRise.exe` + `_internal/`, own Python, no console) that needs nothing installed, built in its own venv (`build_tools/Release/.venv`) from the git-tracked assets minus what the game never loads (`.xcf`, sketches, raw sounds). Before zipping it runs the exe with `MERCHANTS_RISE_SMOKE_TEST` (handled in `main.py`: straight into a new game, quits after that many seconds, exits 1 on an error). In the exe, `main.py` changes to `_internal/` (where assets, saves and `settings.json` live) and writes a `crash.log` next to the exe on an unhandled error. Pushing a tag `v0.1.0` runs `.github/workflows/release.yml`, which builds the same zip and publishes it as a GitHub release. When the game starts loading a new kind of file or folder, check that the exclusions in `build_release.py` don't drop it; the smoke test only catches what a new game loads in its first seconds.

## Architecture Overview

**Merchant's Rise** is a medieval trading simulation built with Pygame. Games are saved to numbered slots and an autosave (`src/persistence/save_manager.py`, `SAVE_VERSION` 3: a compressed, HMAC-signed blob per slot in `saves/`, with the simulation's own `"sim"` block inside; the autosave is written in the background, `save_game(..., background=True)`: the game is copied on the main thread with `marshal` in a few ms and a thread encodes, compresses and writes it, every other save function first waiting for it, `wait_for_save()`; tested in `tests/persistence/test_background_save.py`).

### Core Object Graph

`Game` (src/game.py) is the central orchestrator that owns all major objects and runs the main loop. It creates and holds:
- `GameState` — session data and transient UI state (passed everywhere as `game_state`)
- `Depot` — player inventory, money, bookkeeping
- `Player` — player character with map position logic
- `GameMap` — TMX-based tiled map, camera, collision
- `EventHandler` — dispatches pygame events to keyboard/mouse handlers
- `Simulation` (`sim`) — the headless economy, `src/sim/` (see below)
- Lists of `Good` objects — the 30 tradeable goods of `goods.json`, views of the simulation's goods

### Simulation core

`src/sim/` holds the economy's state and rules without pygame (`docs/sim_core.md` has the structure, the tick order, how to add a system and how to run it headless; `docs/p1_living_market.md` is the design of the living market being built in it, on the branch `p1-living-market`; its phases P1.1 to P1.5 are built (demand, production, 30 goods in chains, the full health report, a minimal UI: needs met per class and tier in the town hall's population stats, and yesterday's demand and supply when a good's box in the market view is hovered, `src/ui/market_flows.py`), then a playtest and the merge; `docs/roadmap.md` has the status of every project and the known loose ends). Prices come from supply and demand (`docs/pricing.md`): `price = reference × volume_factor(stock / target_stock) × noise`, the reference being each good's outside price times a running well wish's shock; the target stock is days of the town's demand. A price moves on four time scales, balanced so that a small trader can live off them while a large one's orders move the market against him (`docs/pricing.md` §2 and §10): the outside price's seasons (`outside_seasons`: firewood, herbs and candles dear in Winter, corn and meat cheap in Autumn, strong enough to stock up for), its slow walk around its mean, news from outside that moves it at a stroke and fades over days (`market.step_news`, per good `news_chance`, `news_size`, `news_reversion` in `goods.json`, reported as `OutsideNews`), and the day's noise (`noise_sigma`, `PRICE_NOISE_PERSISTENCE`). The player pays the market's fee on every trade, a share of what the goods come to (`MARKET_FEE_RATE`, `Depot.trading_fee`). `python -m src.sim.trader` plays a headless trader at several sizes of purse and a hoarder stocking up for the winter: run it, with the sweep, after changing the noise, the news, the fee or the market's depth. Each social class (`ClassState`) has a purse filled by its base income, and a basket of needs in three tiers (`assets/data/needs.json`; above a good's outside price it buys less of it, by an elasticity per tier, and fulfilment still counts against the whole basket) that it buys in hourly slices during market hours (`MARKET_OPEN_HOUR` to `MARKET_CLOSE_HOUR`, `systems/households.py`); merchants import above `reference + transport_cost` and export below `reference - transport_cost` (`market.merchants`); how well each tier was met sets the class's target happiness, which its happiness glides to, and migration follows as before. The player's trades go through `Simulation.trade_with_player` between the slices, so buying up a staple leaves the town short. Workshops (`systems/production.py`, `WorkshopState`) run their building's recipe (`assets/data/recipes.json`, `buildings.json`) for an owner (`OwnerState`; only the town so far, from `assets/data/scenarios/home_town.json`, but no rule reads an owner's kind): their margin at the day's prices sets how hard they run, they hire from one class (when hands are short, shared by workers wanted × margin, `production.share_hands`, a stand-in for P3's wage offers per workshop; a job replaces base income with the class's wage, which rises while hands are short and falls while they are spare, between base income and `wage_cap` in `needs.json`), buy inputs and sell outputs in the same slices, grow after `GROWTH_BUSY_DAYS` busy days within `GROWTH_WINDOW_DAYS` and shrink after `SHRINK_LOSS_DAYS` of losses within `SHRINK_WINDOW_DAYS`; the owner tops them up to working capital and takes the profit, and its `surplus_to` decides the rest (the town: `treasury_with_tribute`, a treasury up to `TREASURY_CAP_DAYS` of its income, the rest paid to the lord out of town). Crowding and migration's floor and ceiling (0.3–1.05) measure against each class's share of the housing. The market place holds no money: the merchants own the stock, every buyer pays them and every seller is paid by them, so the town's money changes by exactly what crosses its border, checked daily as `market_balance` (must be zero). `Simulation` owns the state (`state.py`), one `random.Random(seed)` for all its draws (`rng.py`; no `random.*` calls in `src/sim/`), a `Scheduler` firing the systems on the calendar's ticks (`price_tick`, `hour`, `day`, `week`, `season`, `year`), and an `EventQueue` of what happened (`PriceShockEnded`, `OutsideNews`, `PopulationChanged`, `CapacityChanged`) that the game drains in `Game._handle_sim_events` and shows nothing for yet. `Game.run()` calls `sim.advance_to(game_state.date)` each update; a new game founds the town, establishes the scenario's workshops, and then runs the economy `MARKET_PRESIMULATION_DAYS` ahead (`Simulation.presimulate`). Goods, needs, recipes and building types are defined in `assets/data/` (`goods.json`, `needs.json`, `recipes.json`, `buildings.json`, and `scenarios/`), all loaded and checked by `src/sim/data.py` (`load_definitions`, `load_scenario`). A new game draws a fresh seed (`rng.new_seed()`), shown on the settings' weather page. `Good`, `Town` and `PopulationManager` are pass-through views that keep none of the sim's numbers: a seam, not to be built on. The save's `"sim"` block is `Simulation.to_dict()` with its own `sim_version` (2; version 1 and older saves migrate in `Simulation.load`). `python -m src.sim.run --years 20 --seed 1 --out runs/<name>` writes daily CSVs of the goods, the classes, the workshops and the town plus `meta.json`, `python -m src.sim.trader` says what trading pays, `python -m src.sim.health runs/<name>` checks a run (every check of `p1_living_market.md`'s health table, each a `Finding` registered in `health.CHECKS`: fails for broken books, bad numbers, prices pinned at a clamp, hunger, a runaway money supply or population, workshops long in debt; warnings for prices far from outside, poorly supplied or unhappy classes, dead workshops, structural shortages and a town not running slightly short; plus the tradability measure), and `python -m src.sim.sweep` runs 20 seeds × 50 years in parallel, checks each and writes the table over them to `runs/sweep/summary.md` (`runs/` is git-ignored); it takes the town from `Map1.tmx` through `src/sim/scenario/tmx_town.py`, as the core only takes a plain `TownSpec`. Nothing in `src/sim/` may import pygame, `src/ui`, `src/handlers` or `src/models`.

`GameState` (src/game_state.py) is the shared data bus. It does **not** own logic — it stores flags like `left_side_mode`, `right_side_mode`, `info_window`, `warning`, `contract_acquisition`, `time_level`, and `date`. UI components read and write `game_state` directly rather than using signals/callbacks.

### Screen Layout

Total window: **1920×1080**, 16:9 (SCREEN_WIDTH=1810 + SIDEBAR_WIDTH=110). The windowed presets (`RESOLUTION_PRESETS` in `settings_store.py`) are 16:9 too; a size saved before the frame was widened is mapped to the preset in its place (`_OLD_RESOLUTIONS`).

That frame is scaled to fit the screen (`main.py`), with black bars beside it on a wider one. Fullscreen and the smaller windowed presets are `SCALED` displays stretched on the GPU (`_scaled_window()` lowers pygame's minimum window size and turns off SDL's integer scaling through `ctypes`, which pygame 2.6.1 does not offer); only if that fails is the frame smoothscaled on the CPU. The mouse pointer is therefore a system cursor (`src/ui/cursor.py`, `cursor.use("hand" | "quill" | None)`), sized to the scaled frame, not drawn into it, so it moves over the bars too; presses on the bars are dropped.

The content area (1810px wide) is split into two equal **modules** (MODULE_WIDTH = 905px each). Views lay themselves out from the rect they are given; the depot list was laid out for 825px and hands what is beyond that to its detail panel and value column. The top bar shows `TOP_BAR_VISIBLE_COLUMNS` (6) columns of goods. Each side can independently show `'map'`, `'market'`, `'depot'`, or `'building'` (the town plan). When both sides show the same module, it takes the full width. The top bar (60px) and bottom bar (60px) are always visible. The 110px right sidebar holds the navigation pictograms. When what a module shows changes, however it was changed, `ViewTransition` (`src/ui/view_transition.py`, owned by `Game`) rolls a sheet of parchment down over the part that changed, the new view on the sheet behind the roll and the old one (taken from the screen in `begin_frame()`, before it is cleared) below it, with a short `page_turn_*` for one side and the longest one for both.

Rendering layers in the main loop (src/game.py `run()`):
1. Background fill
2. Left/right content modules
3. Persistent UI bars (`draw_layout`, `draw_right_bar`)
4. Overlays in order: debug overlay → menu, time and sound controls → pause overlay → dropdowns → dialogue → info_window → fading menu → contract_acquisition → minigame → warning/message → coin popups → save indicator (the pointer is a system cursor, not drawn into the frame; see above)

### UI Pattern: Modal Overlays

Any modal dialog (quit confirm, house menus, donation menu, contract overview, population stats) is assigned to `game_state.info_window`. The `EventHandler` routes clicks to `game_state.info_window.handle_click()` and keyboard events to `handle_event()` before routing to the rest of the game. Setting `game_state.info_window = None` closes the modal.

Both settings screens (the main menu's, and the in-game `SettingsWindow` in `src/settings.py`, which opens on a chooser between "Chart Colors" and "Controls", plus "Weather" with the debug overlay on: `WeatherDebugPage` in `src/ui/helper_modules/weather_debug.py`, which shows the simulation's seed and starts any spell (`Weather.force`; nothing jumps, the weather develops towards it as in play, and the spell lasts until it has got there), holds it (`Weather.held`, not saved: the spell does not run out and its fog ignores the hour), strikes lightning at once (`Lightning.strike`), soaks or dries the ground, lets everything fall as snow whatever the season (`Weather.always_snow`, not saved) and lays or clears the snow) have a "Controls" button opening `ControlsOverview` (`src/ui/controls_overview.py`), a list of every key and mouse control written out by hand: when a control is added or changed, update its `LEFT_COLUMN` / `RIGHT_COLUMN` too.

`game_state.contract_acquisition` is a special full-screen overlay that **consumes all input** while active.

### Time System

5 speed levels controlled by `game_state.time_level` (1=paused, 3=normal, 5=fastest); at normal speed (`TIME_STEP_LEVEL_3`) a game day takes 8 real minutes. When the map is visible, speed is clamped to 1 or 3. The simulation time (`game_state.date`) advances via `GameState.update()`, at most `MAX_RECULCULATIONS_PER_SEC` (60) times a second, which returns a `TimeChanges` namedtuple (`minute`, `price_tick`, `hour`, `day`, `season`, `year`). Right after it, `sim.advance_to(game_state.date)` lets the simulation's scheduler fire its own systems for every tick passed (`docs/sim_core.md` has the order); the main loop then does the game's own work on the flags:
- **Every price tick** (`PRICE_TICK_MINUTES`, 30 game minutes, so `PRICE_TICKS_PER_DAY` = 48 a day), in the simulation: each good's noise step and one point on the price chart (`Good.price_history_hourly`, the sim's `price_history_ticks`; saves before `SAVE_VERSION` 2 have their hourly charts filled in on loading)
- **Hourly**: in the simulation, a trading slice in market hours (households and workshops buy, workshops make and sell their share of the day's batches, merchants import and export) and happiness gliding to its target; in the game, the crops' stage and the church bell check
- **Once a season, on its 4th day at 10**: the council sits (`Council.update`)
- **Daily**: in the simulation, the books close (`market_balance`), the outside prices' walk, the well shock, target stocks, workshops pay wages and settle with their owners (treasury, tribute), the classes' income and plan, migration, the workshops' plans, hiring, wages and capacity; in the game, cost-of-living deduction, loans, overdraft penalty, wealth/stock bookkeeping, licence warnings, the merchant rank, an office's stipend
- **Each season**: the reputation fades (`MerchantRank.new_season`), what courting the notables won fades and their grudges with it, feuds are carried on and a term may be up (`Council.new_season`)
- **Weekly, yearly**: nothing yet, in the game or the simulation

The calendar is compressed so a game can span generations: a year is four seasons, Spring, Summer, Autumn and Winter, of `DAYS_PER_SEASON` (7) days each, Monday to Sunday, so a game year (28 days) takes almost four real hours at normal speed. `game_state.date` stays an ordinary `datetime` running on from `START_DATE` (its hours, day spans and saves work as ever), but what a day is *called* comes from `src/sim/calendar.py` (also the one place that says when a tick happens, `tick_numbers()`): `game_date()` (year from `CALENDAR_START_YEAR`, season, day of the season, weekday) and the formats `format_long()` ("Wednesday, 3rd of Spring 1500", the top bar), `format_date()` ("3 Spring 1500"), `format_short()` and `format_with_time()`. Never show the clock's own `.month`, `.year`, `.weekday()` or a `strftime` date to the player: it runs about thirteen times slower than the calendar. `TimeChanges` has `season` and `year` (both from the calendar, for ageing once a year later on); durations sold to the player are in seasons (`LICENSE_SEASON_OPTIONS`, `describe_seasons()`: "2 seasons", "1 year"); the depot's periods are `PERIOD_DAYS` (Daily, Seasonal, Yearly, Total). Lent is the winter from its Ash Wednesday (3rd day) to Easter Saturday, Easter Sunday its last day. Balances set per day before the calendar was compressed (licence fees, loan interest, reputation decay) were converted to keep their cost per day.

### Map System

`GameMap` (src/models/map.py) loads a Tiled `.tmx` file via `pytmx`. Map objects are parsed into typed Python objects: `House`, `Town` (extends House — the town hall), `Church`, `Market`, `Tree`. `Town.initialize_population` moves people into the houses (`STARTING_OCCUPANCY` of each one's `Max_inhabitants`) and hands the simulation a `TownSpec` of their capacities; the people then live in the simulation, which `Town` only shows. The `Camera` class handles zoom and panning.

The `Movements` object layer drives map inhabitants: a rectangle named `Sheep` becomes a grazing zone, and each class in `TMXMap.TRADER_TYPES` (a `Trader` subclass) is placed from objects named after its `TILED_PREFIX`: `<prefix>_Market_Stall` (polygon/polyline he walks at work), and optionally `<prefix>_Homeway_Path` plus the points `<prefix>_Homeway_Start` / `<prefix>_Homeway_End` (his way from the stall to his front door). His `MARKET_NAME` links him to his `Market` booth, which is open only while one of its traders is on his stall path: it shuts as soon as the last of them packs up to go home, so each booth (and each good, via `GameState.is_good_tradable`) has slightly different hours. Each trader keeps his own `MarketHours`, drawn nightly from `MARKET_CLOSE_WINDOW`/`MARKET_OPEN_WINDOW`; goods a trader sells beyond his market's name go in `EXTRA_GOODS`. An optional `margin` float property on a polygon, **in tiles**, pulls the walked outline inwards so the NPC keeps clear of its own edges (`inset_polygon` in `src/models/figurines/patrol_path.py`); a margin too large to fit is ignored. Add a trader by drawing his shapes in Tiled, writing a small `Trader` subclass, and adding it to `TRADER_TYPES`. Several traders may name the **same** `TILED_PREFIX`: they then share the one stall and are put on a `StallRota` (`src/models/figurines/humans/npcs/trader.py`), which draws one of them per calendar day — in the dead of night, when yesterday's is home and nobody is out yet. Only the drawn one leaves the house; the rest stay indoors and hidden all day. The alewife shares the vintner's stall, and the tanner and shepherdess share the weaver's. On the days it is not her turn, the shepherdess keeps her flock in the fold instead of staying in (`TraderShepherdess.at_fold_on`; see the lost sheep). The booth's goods do not change with whoever is minding it.

The `Doors` object layer holds one Tiled **point per front door**, named after the direction a person faces walking out of it (`down`, `up`, `left`, `right`); the Tiled object *id* identifies the door and is what a townsperson remembers. Each `Door` (`src/models/door.py`) keeps three spots on one line: the *threshold* (the Tiled point itself, inside the wall — nobody ever stands there), the *step*, the first spot that many whole tiles out which nothing solid is in (`NavGrid.is_open_at`; it may be hidden behind a neighbour drawn in front of the house, and the grid then opens the shortest way through the hidden cells to the open town, `NavGrid.open_way_out`, so the door is still used), standable, and has a clear line to its own cell centre (a route's first hop is onto the grid, and that hop is validated nowhere else); and between them the *entry*, felt out pixel by pixel as the deepest spot `TMXMap.is_standable()` still allows. A door meeting none of that within `MAX_STEP_TILES` is dropped with a warning naming it, which is a thing to fix in Tiled.

Townsfolk walk entry-to-entry, never onto the point itself — reaching it would put them behind the building, which y-sorts on its own baseline. They come to a **stop at the entry** and only then fade, over `DOORWAY_FADE_SECONDS`, facing the door (`Door.facing_in` / `facing_out`); a doorway fade is not interruptible, not even for a chat.

Fields are objects on the `Fields` layer, rectangles or polygons (`Field`, `src/models/field.py`), whose name picks the crop scattered over them; a name in `BARE_FIELDS` (`Ploughed`) has none (no field uses that now). The Town Plan draws a bare field's furrows upright and names only the sown ones. A crop is a folder `map_sprites/fields/<crop>/` with a `crop.json` listing its growth stages, from the bare field (ground tiles, no sprites) to the ripe crop, at least four, and each stage's variants `<crop>_<stage>_<n>.png` (`crop_sprite_paths()` in `field.py`). Crops and their stages are made in the Sprite Manager's crops area. The crops grow (`CropGrowth`, `src/models/crop_growth.py`, one per sown `Field`): with the seasons of the game calendar: bare (ploughed) through the winter, sown at `FIELD_SOW_DAY` (the 1st of Spring) and growing through the other stages, each an equal part of the time, until it is harvested at `FIELD_HARVEST_DAY` (the end of Autumn) and lies bare again; the stage is worked out from the date alone (`CropGrowth.stage_at`), on starting or loading the game and every game hour (`TMXMap.update_crops`). Each plant is up to half of `FIELD_PLANT_SPREAD_DAYS` ahead of or behind its field, so a field turns over plant by plant within a day or two; a plant at a stage without sprites, the bare field, is not drawn. Plants stand only on the field's inner tiles (all eight neighbours in the field); the edge tiles are its headland, so a field's object in Tiled covers its whole dirt, the ragged edge included. Over the inner tiles lie horizontal furrows (`Field.furrow_overlay`, drawn flat after the ground chunks, half a tile low so the grooves run along the plants' feet, shaded as `plough_field.py` used to bake them): fully shown while the field is bare, wearing away evenly over the sprouting stage, and back in over `FIELD_PLANT_SPREAD_DAYS` around the harvest (`CropGrowth.furrows`); the fade is baked into a copy's pixels in steps of `_FURROW_ALPHA_STEP`, never set as the surface's alpha, which on a per-pixel-alpha surface makes SDL blit it about 8 times slower. The ground under a field is plain dirt. The first `FIELD_STILL_STAGES` stages with sprites (sprouts, young) do not sway in the wind (`Field.still_sprites`). A field's Tiled object may set its own `Sow_day` and `Harvest_day` (days of the year, 0 the 1st of Spring); otherwise the sowing is moved by up to `FIELD_SEASON_JITTER_DAYS`, the same for that field every game (`field_season()`, seeded by its object id), so the fields do not keep step, and the harvest day is the same for all, since the reapers stagger the harvest (below). Nothing of the growth is saved (an older save's `"fields"` is ignored). The plants' places, offsets and variants follow from the object id, so a field looks the same after loading.

The ripe crop is cut by hand (`src/models/harvest.py`, no pygame: the rules and numbers; `harvest_crew.py`: the workers on the map). On the last `HARVEST_DAYS` (3) days of Autumn it stands until it is cut, and each day every field still standing gets one worker, one of the Poor or Commons townsfolk drawn afresh each day, not yesterday's while there are others (`pick_workers`), with hours of his own by the clock (`work_day`: out at 5:30 to 6:30, before dawn, since crossing the town takes a few game hours at a walk; stopping at 16:30 to 17:30). A `HarvestJob` (`Townsperson.job`; while he has one and is indoors or out on it, it runs his frames and `StreetLife` neither counts, sends nor knocks him up; one out strolling when picked finishes the walk first) walks him from his door to the field, through any gate on the way, cuts the plants in a fixed order (`harvest_order`: row by row from the bottom up, back and forth, standing just below each, `STAND_BELOW_PX`), `HARVEST_MINUTES_PER_PLANT` (2.5) of game time each, and in the evening walks him home through the gates again. Heavy rain (`Weather.rain` from `HARVEST_RAIN_FROM`) sends him home; he comes out again if it stops within his hours. A word with the player holds him, the cutting too. At midnight into Winter (`HARVEST_END_DAY`) whatever still stands is cleared (`Field._place_plants`). Because the order is fixed, a field's progress is one number, the plants cut this year (`FieldHarvest.cut`), saved under `"harvest"` (a save without it has none cut). While the map is shown the worker cuts each plant (`HarvestCrew.on_cut`, `Field.mark_cut`); a field with no worker on the map, or after a jump of the clock past `CATCH_UP_MINUTES` (a rest, a minigame, the map hidden), is cut by the time worked (`Harvest.update`, called by `Game._advance_harvest` every update: `worked_minutes` after `COMMUTE_HOURS` of walking, at `HARVEST_MINUTES_PER_PLANT + STEP_MINUTES` a plant), and the worker is put where his day has got to. The furrows show as far as a field is cut. Gates: the worker goes through any gate on his way as every NPC does (`gate_passing.py`, see the gates below); his way is worked out by `GateWays` (`src/models/gate_ways.py`, owned by the crew, `plan_steps` in steps like `route_steps`). The shocks (stooks) are `Shock`s (`src/models/shock.py`), points of Tiled type `Shock` on `Houses` like decorations (`Wheat_Shock_1` to `_14`, `Deco_27`–`29`, placed in the Placing Helper), each belonging to the field it stands on or the nearest: hidden (no picture, no collision, so nothing draws, clicks or routes round it) until the harvest reaches it (`shock_thresholds`: once the plants under its picture are cut, the first with the first plant), all standing for `SHOCKS_STAND_DAYS` after the harvest's end and then gone at once (`HarvestCrew.refresh_shocks`, also every game hour with the crops). The harvest feeds nothing yet (a TODO in `harvest.py`). Tests: `tests/models/test_harvest.py`, `tests/models/test_harvest_crew.py`.

Trees are points on the `Trees` object layer at the bottom-left corner of their sprite (`File_name`, `Stem_Position`, `Stem_Thick`, optional `Scale` to draw one smaller or larger; object type `Broadleaf_Tree` or `Pine_Tree`, which the Town Plan draws round or as a conifer); the `Trees 2`…`Trees 7` tile layers only show them in Tiled and are not drawn by the game, which draws only the `Ground*` tile layers. Those it draws from cached chunks (`GroundChunks`, `src/models/ground_chunks.py`, owned by `TMXMap` as `ground_chunks`): `CHUNK_TILES` square, made once per zoom level and kept least-recently-used, in two passes, the layers up to `Ground_Mid` (its water cells left out) under the animated water and the rest over it, that one laid with premultiplied alpha. The ground is not meant to change while playing; if it ever does, the chunks must be dropped. Whatever the view scales or bakes once per zoom level (chunks, tiles, trees, houses, bridges, the mill's blade, the crops at each sway angle, the water's frames and shoreline cut-outs) is made ahead by `MapWarmup` (`src/models/map_warmup.py`, owned by `GameMap` as `warmup`): `prepare()` while the game loads, the starting zoom and the ground around the player, then `step()` each frame for at most `WARMUP_BUDGET_S`, the chunks just outside the view first and then the other zoom levels, nearest first and the hidden Ctrl ones last. Something new the view scales per zoom belongs in its `_zoom_jobs`, or its first frame stutters. The queued sprites are blitted at `screen_pixel(pos)` (`src/models/pixels.py`, halves always rounded up): Python's `round()` takes halves to even, which made a sprite at an odd world pixel wiggle a pixel against its neighbours while the camera moved (tested in `tests/models/test_pixels.py`). The trees, crop sprites and window lights are looked up near the view in `SpatialIndex`es (`src/models/spatial_index.py`; `TMXMap.tree_index`, `crop_index`, `light_index`, `building_light_index`, filed once at load) rather than all checked each frame; something added to the map while playing must be filed there too.

A building may have a passage through it, as the Golden Sheaf (`House_28`) has under its archway: its Tiled properties `Col_gap_left_pixel` and `Col_gap_width_pixel` (sprite pixels from the object's left edge, scaled like the margins) cut a gap out of its collision box (`House.set_collision_gap`), leaving two boxes either side in `House.collision_rects`, which is what blocks walking (`TMXMap.check_scenery_collision`, `NavGrid`); `collision_rect` stays the whole box for distances, doors, lights and the Town Plan. The archway's opening must be see-through in the sprite; behind the building's base line the walker is drawn under it, so they go out of sight beneath the arch like anywhere behind a house.

Bridges are rectangles on the `Bridges` object layer (`Bridge`, `src/models/bridge.py`): the whole bridge, railings included. `Deck_top` / `Deck_bottom` (tiles from its top) bound the deck, the full-length band feet may stand in; above and below it are the railings, which block, so the only ways on and off are the ends. Over the deck the water does not count (`TMXMap.check_scenery_collision` tests only the parts of a feet box off every deck), and `NavGrid` opens the deck's cells again. Its sprite (`File_name`, in `map_sprites/houses/`) is one *module*, a span with a post at each end: cropped to what is drawn, scaled to the rectangle's height, and laid side by side (each overlapping the last by its end post, so a join shows one) until the row is at least as long as the rectangle, which then grows to that row, centred. It is drawn flat, after the ground and water and under every walker; an optional `<name>_front.png` on the same canvas, holding only the near railing in the same place, is drawn again over them, y-sorted on the rectangle's bottom. Without a sprite file a plain plank stand-in is drawn. A rectangle taller than it is wide is crossed north to south: its deck is given by `Deck_left` / `Deck_right` (tiles from its left), the railings are left and right of it, and its sprite's modules are drawn upright and stacked downwards. The `River_Bridge` carries the eastern road over the river, the `East_Bridge` the south-east road, and the `West_Bridge` the south-west road over the western stream: `Bridge_01.png` modules, the railing in `Bridge_01_front.png`. The `South_Bridge` takes the south road over the southern river north to south and has no sprite yet, so it shows the stand-in. The Town Plan draws a bridge's deck as planks, and water clicks and thrown stones' ripples keep off it.

The harbour cranes hoist freight (`src/models/crane_hoist.py`, no pygame; drawn by `src/ui/layout_modules/crane_view.py`). A building is a crane when its sprite is in `HOISTS` (keyed by `File_name`, as gravestones' designs are; nothing in `Map1.tmx`): a `HoistSpec` gives where the rope leaves the pulley in the sprite's own pixels (scaled with the object's `Scale`), for a gate crane the floor of its hood (`stow_y`), and where the barge floats. So far the treadwheel crane (`House_53`), the covered-jib crane (`House_54`) and the Great Crane (`House_55`). `TMXMap.hoists` holds a `Hoist` each, moved on every frame the map runs (`TMXMap.update_hoists`, from `Game`). The map is frontal, so a jib cannot be seen to turn: loads only go up and down, between a lighter (a small barge) moored under the jib, its loads standing in `BARGE_SLOTS` places, one under the rope, and the jib (hoisted out and held high, or lowered in) or the Great Crane's hood (stowed inside out of sight, or fetched out). A scene (nothing, a load just hanging, a barge to work; no barge by night) is drawn only while the crane has been out of view for `RESCENE_UNSEEN_S`, so nothing pops in or out in sight; in view, a crane with a barge makes trips in working hours (`working_hours`: daylight, no storm or downpour), shoving loads along the barge's floor to and from the hook. The load swings as a pendulum about the rope's top, pushed by the wind with gusts. Loads, hook block and barge (back and front, the loads drawn between so the near side hides their feet) are painted by `build_tools/Sprite_Manager/cargo_painter.py` into `assets/map_sprites/cranes/` at twice their world size; all of a crane's pieces sort on the barge's waterline. Nothing of it is saved.

Fishing spots are points on the `Fishing` object layer (`FishingSpot`, `src/models/fishing_spot.py`, `TMXMap.fishing_spots`), each in the water just off where the player stands, named as the player reads it (a point not in the water is left out with a message). So far `Wide River`, `River Fork` and `Harbor Pier`. Within `FISHING_REACH_TILES` of one, a click on the water offers "Go Fishing" under the spot's name (`show_water_menu`, which calls `open_fishing`, once a day over all spots). While the day's fishing is still to be done, golden rings spread on the water there (`_draw_fishing_spots` in `map_view.py`); the Town Plan marks explored spots with a fish (`glyphs.fish`), named when hovered, and likewise the chopping stump (`TMXMap.chopping_stump`, the house object named `Stomp`) with a stump and axe (`glyphs.chopping_stump`; `TownPlan._draw_minigame_marks`, `_minigame_mark_at`, a new minigame's place goes there too). A spot may be fished from a boat moored at it instead: a building on `Houses` whose `Fishing_spot` property names the spot (`House.fishing_spot`, `FishingSpot.boat`, linked in `TMXMap._load_fishing_spots`), as the `Fishing_Boat` (`Deco_30`, "Fishing Boat") off the harbour pier's end is the `Harbor Pier`'s; there a click on the water offers no fishing (`fishing_spot_near` skips such spots), the boat's house menu offers "Go Fishing" (`open_fishing`, the same once a day), and the boat glows (`inject_available_glow_into_queue`) instead of the rings. A building whose `Afloat` property is true (`House.afloat`, as the fishing boat and the three boats moored in the harbour, the `Trading_Cog` (`Deco_31`) at the south quay, the `Sailing_Boat` (`Deco_33`) and the `Rowing_Skiff` (`Deco_32`)) bobs and rocks on the water: `src/models/afloat.py` (`motion`: `BOB_PX` up and down as the cranes' barge, `ROLL_DEG` either way in steps of `ROLL_STEP_DEG`, each boat out of step by where it lies, a boat longer than the fishing boat, `REFERENCE_LENGTH_PX`, its collision box's width, moving less and slower by the square root of how much longer, `size_factor`), drawn turned about the middle of its foot by `src/ui/layout_modules/afloat_view.py` (`afloat_pose`, the turned pictures kept), the glows going with it. All spots play the same pond scene so far.

`NavGrid` (`src/models/navigation.py`) rasterizes house/tree collision rects and the water polygons into one walkable cell per tile, and answers `find_route()` with A* plus line-of-sight smoothing. It also blocks what collision does not: cells where `OCCLUSION_COVER` of a walker's sprite would be hidden behind a building drawn in front of them. Coverage is counted in painted pixels via `pygame.mask`, which is what distinguishes a wall from a fence. Without this, routes run through the band of walkable ground behind tall buildings and walkers simply disappear into them. Only a door's way out may run through such ground (see the doors above; `NavGrid.solid` keeps what collision alone blocks). It is built once, after every blocker has been parsed, and is told the walkers' sprite size so it knows how much of them there is to hide.

The player can still walk behind buildings: when what is drawn in front of him (not lights, not other figures) covers `SILHOUETTE_FROM` of his painted pixels for `SILHOUETTE_DELAY_S`, `PlayerSilhouette` (`src/models/player_silhouette.py`, owned by `GameMap` as `player_silhouette`, tested in `tests/models/test_player_silhouette.py`) fades in a faint whitish outline of him, drawn after the lighting and fog (fainter with the map's light at night, down to `SILHOUETTE_NIGHT_FLOOR`), and fades it out once he is clear.

`FogOfWar` (`src/models/map_fog.py`, owned by `GameMap` as `map_fog`) remembers which land the player has been near, for the Town Plan only — the map view itself is never fogged. `FOG_CELLS_PER_TILE` cells per tile each remember how well they have been seen (0–255), revealed in a circle of `FOG_REVEAL_RADIUS_TILES` around the player that fades out over `FOG_FADE_TILES`, and never forgotten. It is stored in the save under `"fog"` and restored with `GameMap.restore_map_fog()` once the player is in place; a save without it starts with nothing explored.

`Ambience` (`src/models/ambience.py`, owned by `Game`) keeps the map's ambient loops going, each on a mixer channel reserved in `Game.init_pygame()`, paused while the map is hidden or the game paused (but not while a minigame, which pauses the game, is open): the mill's gears by the distance from its walls (`MILL_VOLUME_BY_DISTANCE`), birdsong in the woods by day (`BIRDS_BY_HOUR`), crickets in nature by night (`CRICKETS_BY_HOUR`), the rivers and the sea by the distance to them (`RIVER_VOLUME_BY_DISTANCE`, `SEA_VOLUME_BY_DISTANCE`), the market crowd by the distance to the nearest *open* booth (`MARKET_VOLUME_BY_DISTANCE`), so it follows the traders' hours, each booth's crowd swelling over `MARKET_SWELL_HOURS` of game time after it opens and dying away as long after it shuts, each market (booths within `MARKET_GROUP_TILES` of each other, `group_markets`) with its own recording (`MARKET_LOOPS`, the biggest market first), the quiet streets where houses stand close together (`STREETS_BY_HOUSES`, booths not counted, so a lone house is silent; it gives way to a market's crowd), and the rain by how hard it rains (`RAIN_VOLUME`; the birds and crickets hush under it). The rain is four recordings, `amb_rain_light_2_loop`, `amb_rain_light_loop`, `amb_rain_medium_loop` and `amb_rain_heavy_loop`, each on its own channel with a volume curve over `Weather.rain` (`RAIN_LAYERS`), so they fade into one another from drizzle to downpour. Every loop glides to its volume (`LOOP_GLIDE_PER_S`) rather than jumping. Owls (`Owls`, `src/models/owls.py`, owned by `Game`) are one-off calls rather than a loop: an `owl_*` once in `OWL_EVERY_HOURS` of game time on the map, the clock running only at night (`OWLS_BY_HOUR`) and as fast as the player stands in a wood (`Ambience.trees` against `FOREST_FULL_COVER`), slowed by rain (`RAIN_HUSHES_OWLS`); each near or far by chance (`OWL_LOUDNESS`) and a little to one side (`OWL_PAN`). Dogs (`Dogs`, `src/models/dogs.py`, owned by `Game`) bark the same way in town (`Ambience.town` against `TOWN_FULL_COVER`), once in `DOG_EVERY_HOURS` (2 to 3 a day), by day and night: a `dog_bark_far_*`, a bout of `DOG_BOUT_BARKS` single `dog_bark_distant_*` barks, or at night (`DOG_CHORUS_HOURS`) now and then the village's dogs (`dogs_far_village_night`). These three, and the coughs, count only game time spent on the map (`MapClock`, `src/models/map_clock.py`). There is no forest, town, river or sea object: a `Cover` works out once, at load, for every tile how much is around it — the stems of the `Trees` for the woods, the buildings (not fences or decorations, `NOT_TOWN_BUILDINGS`) for the town, nature being where the town is not — so a wood grown with the Forest Builder sings by itself; `split_water` tells the sea (open water, with the bay and the harbour) from the rivers (narrow water) by the water tiles' shape, `open_sea` keeps the waves to the sea near the map's edge (`OPEN_SEA_TILES`), so the bay and its harbour are calm, and a `Distance` per kind says how far every tile is from it.

`Weather` (`src/models/weather.py`, owned by `Game`, saved under `"weather"`) goes through spells of `WEATHER_SPELLS` in game time (clear and overcast, showers of drizzle, rain (3 to 24 hours, half of them under 5: a spell's `hours` may give a median length, the long ones then growing rarer), sometimes a downpour, now and then a thunderstorm (`storm`), and clearing, 1 to 2 a week, and mist, now and then thickening into fog, after a clear spell or a shower; each spell lasts some hours and is followed by one drawn from its `next` weights); the seasons bend that (`WEATHER_BY_SEASON`: per season, factors on the `next` weights and on a kind's `hours`, by the season a spell starts in), and on all fog (`"fog"`, the spells' and the wet ground's): Summer has less rain, no mist or fog at all and the only thunderstorms (most of its showers end in one, about one storm every other summer), Autumn twice the rain and three times the fog, Spring and Winter as `WEATHER_SPELLS` has it but without storms; a spell forced from the debug page keeps its fog whatever the season; its `rain`, `clouds` and `wind` glide towards the spell's at `WEATHER_GLIDE_PER_HOUR`, so showers set in and pass off; the rain waits for its clouds (`Weather.rain_ceiling()`: none below `RAIN_FROM_CLOUDS` of cover, the spell's rain once its clouds are there), so the sky clouds over before it rains and the rain eases off before it clears. Its `fog` (0 to 1) glides slower (`FOG_GLIDE_PER_HOUR`) towards the spell's `fog` or the wet ground's own mist once the rain has stopped (`FOG_FROM_WETNESS`), whichever is more, times what the hour allows (`FOG_BY_HOUR`: thick at night and before dawn, mostly burnt off by noon). `Fog` (`src/models/fog.py`, owned by `GameMap` as `fog`, advanced only while the map runs; not the fog of war, which is `map_fog`) draws it in layers after the lighting and before the rain: an even veil, banks from three layers of tiling noise drifting at their own speeds with the wind (soft round bumps, not a grid, since the banks' threshold would show a grid's creases), gathering over water, thinner round the player (`FOG_CLEAR_RADIUS_TILES`), loose wisps (`FOG_WISPS_PER_MEGAPIXEL`) and a glow round every lit window. Veil, banks and clearing are worked out in gray at 2 pixels a tile and smoothed up as a multiply and an add, 15 times a second or when the camera crosses one of those pixels; its colour follows the scene's light. Clouds dim the map through the day/night overlay (`daylight.overcast()`, `CLOUD_TINT`, less so at night). A thunderstorm's `storm` level (only the `storm` spell has one; it glides like the clouds and is saved) dims it further (`STORM_TINT`) and brings `Lightning` (`src/models/lightning.py`, owned by `Game`, real seconds while the map runs): strikes every `LIGHTNING_EVERY_S` at full storm, none below `LIGHTNING_FROM_STORM`, each flickering once to three times (`FLICKERS`; `map_view` adds the flash over the map, up to `LIGHTNING_FLASH_ADD`) and mostly followed after `THUNDER_DELAY_S` by one of the `thunder_*` sounds, the later the softer (`THUNDER_VOLUME`), never the same twice running. `Rainfall` (`src/models/rain.py`, owned by `GameMap` as `rain`, only advanced while the map runs) keeps the drops in world space around the view, `RAIN_DROPS_PER_MEGAPIXEL` of them at full rain, each landing as a splash, or as a ring on water. The splashes and rings on the ground are drawn on the ground (`Rainfall.draw_ground`, after the puddles and before the render queue), so whoever and whatever stands over them hides them and the lighting darkens them; the falling drops and the splashes on roofs are drawn over everything after the lighting, dimmed by it, in one `blits()` call. Drops also burst faintly off the tops of people and animals out of doors (`FIGURE_SPLASHES_PER_PX_S` per pixel of their width, `Rainfall.figure_splash_entries`, put in the render queue just over each figure, the top of its sprite looked up only in the columns hit). On a building a drop only splashes inside a roof: polygons on the `Roofs` object layer, named after their building (`TMXMap.roofs`, `src/models/roofs.py`, which files every building's painted pixels and the roofs by tile); elsewhere on a building's sprite it ends unseen. A polygon there of Tiled type `Hole` is where a roof is open (a courtyard): it cuts the roofs named after the same building that it overlaps (`match_holes`), for the rain and the snow caps alike. A new building needs its roof drawn (`place_building.py roof`, see the place-building skill). The ground's `wetness` (in `Weather`, rising with rain by `PUDDLE_FILL_PER_HOUR`, drying by `PUDDLE_DRY_PER_HOUR`) drives `Puddles` (`src/models/puddles.py`, owned by `GameMap` as `puddles`): each wet spell, once the ground was dry, scatters new ones over a few updates (at most `PLACE_BUDGET_S` of each), mostly on road and paving (`PUDDLE_PATH_TILES_EACH`; the tiles come from `TownPlan.trodden_tiles()`, the rest get `PUDDLE_OFF_PATH_SHARE`), never touching a building's or tree's collision box or painted pixels (`pygame.mask`), water, bridges or fields. Each shows from its own wetness threshold and grows to full size; some are longer (`PUDDLE_WIDE_SHARE`, `PUDDLE_WIDE_TILES`, never taller). It is drawn flat on the ground before the render queue: a multiply (so the ground shows through), the sky, then whatever in the queue stands behind or in it, mirrored about its base line and cut to the water (a mirrored building's lit windows too, each light filed once under the building it is on, as a glow `Puddles.draw` returns for `_apply_lighting` to let through), then a thin pale rim; raindrops ring on it, and so does anyone walking through it (`Puddles.update_walkers()`, each `RIPPLE_STEP_PX` walked in the water a step's rings, cut to it, a few droplets thrown up, and the reflection shaken sideways in bands while they last). Under the puddles, `WetGround` (`src/models/wet_ground.py`, owned by `GameMap` as `wet_ground`) darkens the ground by how wet it looks (`wet_level()`: the wetness plus a little of the rain), with a tint per kind of ground (`WET_TINTS`, from `TownPlan.ground_masks()`), unevenly: each spot darkens at its own threshold (smooth noise), lowered round every puddle, so the ground wets and dries in blotches and each puddle sits in a damp patch. It is kept at 4 pixels a tile and the view's part smoothed up in one piece, made again only when the camera has moved a quarter tile or the wetness changed. In Winter the rain falls as snow: `Weather` splits what the spell lets fall into `rain` and `snow` by the share the day of the year turns to snow (`snow_share_at()`, `SNOW_BY_DAY_OF_YEAR`: sleet on the first and last days of Winter), so everything that reads `rain` (the rain's drops and sounds, the wet ground, the puddles) simply stops in the snow, which is silent. Snowfall builds up `snow_cover` (`SNOW_FILL_PER_HOUR`, saved), which lies as long as it is cold enough to snow and thaws after (`SNOW_MELT_PER_HOUR`, faster in rain), the meltwater wetting the ground (`SNOW_MELT_WETS`), so a thaw leaves puddles; the puddles go by `Weather.puddle_level`, the wetness the snow does not hide. `Snowfall` (`src/models/snow.py`, owned by `GameMap` as `snow`) draws the flakes like the rain, in world space, slow, swaying and carried by the wind (`SNOW_FLAKES_PER_MEGAPIXEL` at full snow), the near ones settling and fading where they land (on the ground under everyone, on roofs over them). `SnowCover` (`src/models/snow_cover.py`, `GameMap.snow_cover`) lays it on the ground after the wet ground: every spot has a depth of cover it turns white at (`src/models/snow_flecks.py`), the lower of a tiling pattern of broken flecks in clumps, shifted earlier or later by smooth noise, and a blanket from `BLANKET_FROM` on, so a first snow lies as scattered flecks gathering into uneven patches and only deep snow is an even white; later on the roads, paving and forest floor (`PENALTY`), none on water. It is made in chunks of `CHUNK_TILES` per zoom and depth step, a few a frame within `BUILD_BUDGET_S`, and drawn one blit a chunk. `RoofSnow` (`src/models/roof_snow.py`, `TMXMap.roof_snow`) puts a snow cap over every building's `Roofs` polygons, made from its sprite and queued just over it, building up the same way between the two levels of `SNOW_ROOFS_FROM` (made within `BUILD_BUDGET_S` a frame, `begin_frame()`, an older look standing in meanwhile). Trees and crops get no snow yet. With the debug overlay on, F9 starts the next kind of weather, and the settings have a weather page (see the UI section).

The length of the day follows the seasons through the *sun hour* (`src/models/daylight.py`, `sun_hour()`): everything that goes by daylight is set out for a day of Spring or Autumn (full daylight 8:00 to 17:00, night 21:00 to 4:00), and `sun_hour()` turns the clock into the hour of such a day that looks the same. At midsummer the dawn comes `DAYLIGHT_DAWN_SHIFT_HOURS` earlier and the dusk `DAYLIGHT_DUSK_SHIFT_HOURS` later, at midwinter the other way round, by degrees over the year (a cosine of the calendar day, so a season's turn shows no jump); in Autumn and Winter the dawns and dusks also last up to `DAYLIGHT_TWILIGHT_STRETCH` longer, most where Autumn turns to Winter (`twilight_stretch()`). The light also has a mood by season (`season_tint()`, `SEASON_LIGHT_TINT`, multiplied into the map's light at every hour, blended between the seasons' middles): clear in Spring and Summer, warm and reddish in Autumn, cold and bluish in Winter; so in Autumn and Winter the lighting overlay is drawn by day too, as it is at night. The map's light (`ambient_light()` in `daylight.py`, its keyframes `AMBIENT_KEYFRAMES`; the minigames played outside are lit by it too, through `Outdoors` in `src/models/minigames/outdoors.py`: the sky at the hour with the sun or the moon (its phase once a season) and the stars, the light dimmed by clouds and storm like the map's and lifted a little at night, lamps of the scene's own lit after dusk, the game's rain, snow (and the snow lying), fog, clouds and lightning with thunder; the woodhacking's scene is the first to use it), window and building lights, chimney smoke, the knock's night check, birds, crickets, owls, the dogs' night chorus and `FOG_BY_HOUR` go by it; what goes by the clock (markets, townsfolk going out, the church bell) does not. Something new that should follow the daylight reads `sun_hour(date)` instead of `date.hour`.

`StreetLife` (`src/models/town_life.py`) keeps `STROLLERS_BY_DAY` / `STROLLERS_BY_NIGHT` townsfolk out at a time, fewer while it rains (`STROLLERS_IN_RAIN_*`, from `Weather.rain` reaching `STROLL_RAIN_FROM`; those out finish their walk). A `Townsperson` (`src/models/figurines/humans/npcs/townsperson.py`) steps out of their door fading in, walks a cached door-to-door route — stopping to look at something now and then — and fades out into the door they arrive at, which becomes their home for the next outing. Nobody is out twice, because there is only one object per person. There is no `Townsperson` subclass per person: `discover_townsfolk()` creates one per sprite folder holding an `npc.json`, so adding a townsperson is adding the folder. Their positions are session state, not saved. `StreetLife.update()` only directs; the townsfolk themselves are walked by `update_npcs()` like any other NPC. A route not walked before is worked out over several frames (`NavGrid.route_steps()`, a generator yielding every `SEARCH_CELLS_PER_STEP` cells searched or `SIGHT_SAMPLES_PER_STEP` sight-line samples; `find_route()` runs it in one go), at most `ROUTE_BUDGET_S` of each, while whoever is going out waits indoors: done in one frame, a long one took 20 to 40 ms here and far longer on a slow PC.

Each door is handed to the building whose collision rect its point sits in (`TMXMap._attach_door_to_house`), which is what connects a knock to the people behind it. Knocking on a house somebody is home in has a `KNOCK_ANSWER_CHANCE` of being answered: `StreetLife.answer_knock()` picks one of its residents, who opens the door, steps onto the doorstep, stands there `KNOCK_ANSWER_SECONDS` and goes back in. Talking to them holds that wait for as long as the bubble is open.

A *homebody* (`Homebody`, `src/models/figurines/humans/npcs/homebody.py`) keeps to one house instead: a townsperson's folder whose `npc.json` names a `"home"` (a building's Tiled name; he uses its first door, which `StreetLife` then leaves out) is not sent strolling (`discover_townsfolk` skips it) but settled by `TMXMap._load_homebodies` once the grid and doors are there. He steps out in the morning and goes in in the evening by the daylight (`sun_hour` within `OUT_WINDOW` / `IN_WINDOW`, drawn daily), spends the day walking his `<prefix>_Yard` polygon on the `Movements` layer like a trader his stall (resting `IDLE_*_MINUTES` at each spot, looking out from the house), and now and then (`WALK_CHANCE` per rest, at least `WALK_GAP_MINUTES` apart) walks out to one of his `<prefix>_Walk_1`, `_Walk_2`… points, lingers and comes back; the ways between are worked out once at load (`TMXMap._homebody_route`: straight where clear, else `NavGrid.find_route`). The prefix is his `"name"` unless `"tiled_prefix"` says otherwise; without a yard he stands on his doorstep. A `"stand_in"` folder lends him its looks while his own has no standing sprite, `"sentences"` names a sentence file of his own (said `OWN_LINE_CHANCE` of his chats), and `"introduces"` a minigame he shows the player. The first is Osric (`commons_osric`, so far only standing sprites: the woodcutter trader's, grey-haired and in dark grey), the trader's old father, about the `Wood Chopper` shed by the stump. The woodhacking is not open until he has introduced it (`Statistics.minigames_introduced`, saved; an older save that has chopped wood counts as introduced; with nobody on the map to introduce a minigame it is open, `minigame_introduced` in `house_click_menu.py`): till then the stump's "Chop Wood" only says to ask him, and he glows instead of it, a gold "!" bobbing over him (`quest_marker.py`, as over everyone who glows for having a talk, a quest or a thanks for the player). His menu has "Need a hand with the wood?" (the introduction's `talk_option`), pages of `FigurineConversation` (a speech bubble with the player's answers) from `INTRODUCTIONS` in `src/models/introductions.py`, where agreeing introduces it and "Hand me the axe" starts it; afterwards "Lend a Hand" (`lend_a_hand`, through `MINIGAME_OPENERS`) starts the day's woodhacking (`open_woodhacking`, as the stump's option does) or he says it has been done today. Where he is, is not saved. Once a woodhacking session has been finished, his son, the woodcutter at the wood market, glows under a "!" and offers "Talk" too: a `Thanks` (`THANKS` in `src/models/thanks.py`, matched to a trader by its `giver`, his `TILED_PREFIX`) for helping his father, with a gift of 3 Wood, "Accept his gift" (`Depot.receive_goods`: into the pack first, what it cannot hold into the storage as a purchase would go, all or nothing, booked as bought for nothing, and "+3" with the wood's picture rises over the cursor like a trade's coins, `on_goods_received` in `src/ui/transaction_feedback.py`, for goods that come without money changing hands, never for trades; without room a warning and he asks again later) or "No thanks needed!", which earns `Thanks.reputation` (1) instead; either ends it for good (`Statistics.talks_done`, saved). Beside each answer the bubble shows what it brings (`FigurineConversation`'s `badges`, from `thanks_badges`): "+3" and the good's icon, "+1" and a small gold laurel for reputation (`reputation_badge_icon`). The scripted talks are in modules of their own: the pieces of a page and its answers in `src/models/talks.py`, each kind's texts in its own model module, the flow (what an answer does) in `src/ui/helper_modules/figurine_talks.py`, the bubbles themselves in `figurine_bubbles.py`; `figurine_click_menu.py` only offers them in the menu.

Every NPC has a `GENDER` (`"male"` or `"female"`, `NPC.GENDER`): a townsperson's comes from the `"gender"` in their `npc.json`, a trader's is a class attribute (the alewife, farmer, herbalist, shepherdess and weaver are women). `Coughs` (`src/models/coughs.py`, owned by `Game`) uses it: every `COUGH_EVERY_HOURS` of game time spent on the map (1 to 2 a day; time off the map or a jump of over an hour does not count) a random NPC out of doors within `COUGH_MAX_DISTANCE` of the player coughs a `cough_man_*` or `cough_woman_*`, softer the farther off (`COUGH_FALLOFF`); with nobody near it tries again after `COUGH_RETRY_HOURS`.

Clicking a figurine opens its menu (`src/ui/helper_modules/figurine_click_menu.py`). "Chat" says a line of their class's sentence file in `assets/texts/NPCs/` (plus the traders' file for a trader), or with a chance of `RUMOUR_CHANCE` (`sentences.py`) one of `sentences_generic_rumours.txt` allowed to them: hints at how the game works, in the townsfolk's words, so when a mechanic changes, check they still hold. A rumour names who may say it, as `• [Poor, Commons, Traders] The sentence.` (social classes, and `Traders` for anyone who trades, whatever their class; without brackets anyone may). In any of these files, a line about the speaker's marriage uses a placeholder of `SPOUSE_WORDS` (`sentences.py`), as `my {spouse}`, filled in by `NPC.GENDER`: a man has a wife, a woman a husband. Anyone whose `SOCIAL_CLASS` is `"Poor"` is also offered a coin: `ALMS_COIN` is booked as a donation under `ALMS_CATEGORY` ("Alms", a bookkeeping category of its own), with the donation feedback (`on_money_donated`, which for a gift of one coin plays `coin_flip` or a `coin_single` variant, by even odds, instead of the falling coins; church and town donations use it too), and the speech bubble then opens with their thanks, a line of `assets/texts/NPCs/sentences_thanks_alms.txt` (`NPC.thanks_line`), a `•` bullet per sentence like the other sentence files.

### Town Plan

The `'building'` view (sidebar tooltip "Town Map"; the `'map'` view's is "Explore") shows the whole map as an old paper plan of the town, in its own package `src/ui/layout_modules/town_plan/`. `TownPlan` (`view.py`) is owned by `Game`; it is told `begin_frame()` each frame and only takes input (wheel zooms towards the cursor through `ZOOM_LEVELS`, dragging pans) while it was drawn, routed from `EventHandler` ahead of the usual click handling. The legend keeps the bottom-right corner unless the player's mark comes near it; then it moves to the first of bottom left, under the compass or under the title that is clear of the mark (`_place_legend`, with a gap between `LEGEND_STAY_CLEAR` and `LEGEND_MOVE_CLEAR` so it doesn't hop back and forth). The player can also drag it anywhere on the sheet, and it goes back to its corner the next time the plan is opened. Nothing on it is drawn by hand: `terrain.py` averages the `Ground*` tile layers down and picks water, sand, road, cobbles and forest floor out by colour (`GROUND_*` in `style.py`) into `pygame.Mask`s, and `landmarks.py` turns the `House` objects into roofs, stalls, fences and named places, and finds where the bay's and the wood's names fit. `engraving.py` inks that once per zoom level, at the level's own resolution (so lines stay fine); `TownPlan.prepare()` builds all of it while the game loads, so opening or zooming the plan never stalls; what changes while playing — the player's mark, the map camera's frame, packed-up stalls, owned warehouses, names, the hover tooltip — is drawn on top each frame (`ornaments.py`), on parchment whose grain is pinned to the land, so it moves when dragged. Only explored land is charted: `TownPlan._cover_unexplored()` lays the blank paper (a shade darker, `UNCHARTED_TINT`) over the rest through the fog's veil, and unexplored names and buildings are neither labelled nor hoverable. With the debug overlay on (`show_map_debug`), a radio switch under the title panel ("Explored land only" / "Everything", `TownPlan.reveal_all`, not saved) lifts that cover to show the whole map. A new building, road or patch of water in Tiled shows up on the plan by itself; a new *kind* of building needs a case in `landmarks._kind`. Colours, fonts and names are in `style.py`.

That parchment is `src/ui/paper.py`'s `draw_paper()`, shared with the loading screen and the market and depot chart backgrounds: a seamless grain tile laid from an anchor point plus browned edges for the rect, made from any base colour (`PARCHMENT*` in `colors.py`; the charts use `SANDY_BROWN`). `PAPER_GRAIN` sets how strongly it shows.

### Trading System

`Depot` (src/models/depot.py) manages money, `good_stock` (Dict[str, int]), and FIFO `purchase_history` for profit tracking. Trading licences are a guild's: each good's `license` in `goods.json` names the licence it is traded under (its own, or its chain's head: Flour and Bread under Wheat, Tools under Iron), and `Depot.trading_licenses` is keyed by licence (`Depot.license_of`, `has_license(good)`); each expires after a duration, its fee per season being the head good's `license_fee`. Every list of goods (the depot's accounts, the trade cards' quantities, the licence overview, the booths' extra goods via `sold_at` and `Market.SOLD_AT`) comes from `goods.json`; `constants.py` keeps no per-good lists. The top bar shows the goods pinned with a right-click on a good's box in the market view (`GameState.pinned_goods`, saved; a new game pins the first `TOP_BAR_DEFAULT_PINS`; a folded corner on its market box, `src/ui/pin_marker.py`, marks them) and those held, in goods.json order; past `TOP_BAR_VISIBLE_COLUMNS` columns its arrows scroll it. Trading is done on the market view's **trade desk** (`src/ui/layout_modules/trade_desk.py`, drawn by `draw_chart` in the chart's right `DESK_WIDTH`): a card for each good in the chart (three at the most, `GameState.trade_goods()`, in the order chosen, so F1/F2, F3/F4, F5/F6 are the first, second and third card's Buy and Sell), joined to the end of its line. A card shows the price and its change in a day, the market's stock, what the player holds, what it was bought at and its gain, a quantity (typed after a click, the wheel over the card, `/2`, `-`, `+`, `x2`), Buy and Sell with what the order comes to, fee and slippage included, under each the price per unit and the most that could be traded ("Max" / "All", a click takes it as the quantity), and a last line saying why an order cannot be placed or, with the pointer on a button, where it leaves the price and what a sale earns. Those numbers are `src/models/trade_offer.py` (`buy_offer`, `sell_offer`, `max_buy`, `market_block`; no pygame); a greyed button is exactly an order `Depot.buy` / `sell` would refuse. The chart shows the holdings too: a dashed line at what a charted good's stock was bought at, an arrow on its line wherever the player bought or sold it (`Depot.trades`), and an arrow at the line's end for where the hovered order would leave the price. The hitboxes are filed each frame in `GameState.trade_buttons` (`<part>_<section>`), merged into the main loop's `buttons`; `trade_card_order` in `mouse_handler.py` places an order for the buttons and the F keys. Orders need the player in a market square and the game running. Each market square remembers the goods charted while the player was there (`GameState.quicktrade_slots`, saved) and puts them back in the chart on coming to it (`Game._chart_market_goods`). The bottom bar only shows the town's population. A good's quantity on its card starts at about `QUICK_TRADE_LOT_VALUE` worth (`quick_trade_quantity()` in `game_state.py`). `good_stock` is the total; where it lies is kept in storage **slots**, each holding up to its size of one good only, so the room left in a part-filled slot is lost to every other good. The starting storage has `STARTING_STORAGE_SLOTS` of `SLOT_SIZE` (`Depot.starting_slots`, its filter `Depot.starting_accepts`, saved); it is no building of its own, but once the intro is done it is kept in Uncle Gared's shop (`intro.is_found_shop`, named `SHOP_NAME`), whose house menu then has "Manage Inventory" on it like a warehouse's and which the Town Plan rims in gold as the player's (every per-storage method of `Depot`, `warehouse_slots`, `carry_from_warehouse`, `store_in_warehouse`, `set_accepted_goods`, `set_slot_reservation`, `storage_accepts`, takes `START` as well as a warehouse's Tiled id); each warehouse declares its own in Tiled (`Buy_slots`, `Buy_slot_size`) and, once owned, keeps them in its `properties["warehouses"]` entry (`"slots"`, `"slot_size"`). `buy` checks `room_for()` and tops up slots already holding the good before taking empty ones, going through the storages in `Depot.storage_order`, the player's priority list (keys `START` and the warehouses' Tiled ids; the starting storage first and warehouses as bought, until reordered with `move_in_priority`); `sell` goes through it from the other end, least-filled slots first. Filters steer where goods may go: a warehouse accepts all goods or some (its entry's `"accepts"`, `set_accepted_goods`), and a slot may be reserved for one good (its `"reserved"`, `set_slot_reservation`), which it alone then takes whatever the warehouse accepts (`Depot.slot_takes`); they never throw out what is already stored. A purchase only the filters stop is refused with its own warning (`room_for(..., filtered=False)` tells it apart); `settle_storage()` repacks them after loading if they disagree with `good_stock`. The player's pack (`Depot.pack_slots`, `PACK_SLOTS` of `PACK_SLOT_SIZE`) is slots too, its goods part of `good_stock`: purchases never go into it, sales take from it last, and `total_capacity()` counts it. An owned warehouse's house menu (and the uncle's shop's) has "Manage Inventory", which opens `WarehouseInventory` (`src/ui/helper_modules/warehouse_inventory.py`): the warehouse's slots over the hands', a click moving a slot's goods across (`carry_from_warehouse`, `store_in_warehouse`, which follows the filters too), a right-click one unit; a warehouse's slots take at most `MAX_SLOT_ROWS` (4) rows, more columns and a wider window instead (`SlotSection`'s `max_rows`, tested in `tests/ui/test_inventory_layout.py`), so 32 slots still fit the screen. Over them is a settings strip: the priority list with buttons moving this warehouse earlier or later, and the goods it accepts; the funnel in a slot's corner reserves it. Goods are picked in a `GoodsPicker` (`goods_picker.py`). `PlayerInventory` (`player_inventory.py`, opened with I or from the menu of a click on the player's figure) only shows the hands. Both are an `InventoryWindow` (`inventory_window.py`) of `SlotSection`s, drawn into a cached panel redrawn only when the slots or the footer change. The `Good` (src/models/good.py) is a view of the simulation's `GoodState` (current price, market quantity, per-tick/daily price history) plus its chart colour and visibility. The church's house menu also has "Donate Goods" (`FeastMenu`, `src/ui/helper_modules/feast_menu.py`): the meals in `CHURCH_FEASTS`, each a set of goods given out of `good_stock` by `Depot.donate_goods()`, which takes them like a sale (slots, oldest purchases first) but with no trade cycle, and books their market price on the day as a donation under `CHURCH_FEAST_CATEGORY` (and in `Statistics.goods_donated` / `goods_donated_value`); money does not change, and if any good falls short nothing is taken and a warning names what is missing. How prices are calculated, and where each part of that lives, is in `docs/pricing.md`: update it when the price model changes.

### Depot view

With the depot on both sides, the left module shows its charts (`draw_depot_chart` in `src/ui/layout_modules/depot_view_chart.py`) and the right its accounts (`draw_depot_view`, `depot_view.py`, with the row's details in `DepotViewDetail`, `depot_view_detail.py`); with the depot on one side only, the accounts. On both sides they share one sheet under one title, "Depot" (`draw_depot_sheet` in `ledger_style.py`, a brass rule down its middle; the halves are drawn with `framed=False`, the chart's title then heading its plot); on one side the accounts are a sheet of their own. The sheets are of the guild's records' kind in a theme of their own, the counting house (`ledger_style.py`: `COUNTING_HOUSE`, green baize and brass, the frame's band an exchequer's chequered cloth, `CHEQUER` in `tutorial_sheet.py`, in the slimmer frame `SLIM_FRAME` (`FrameGeometry`; the records keep `BROAD_FRAME`); its fonts, the framed sheets made once per size and title, the parchment tooltip `note`). What a chart shows is `depot_chart_data.py` (no pygame; `build_chart` returns a `ChartData`): the books are midnight snapshots, so every series is dated backwards from today, the last entry being how yesterday closed, and today is added from the live figures as "so far" (its bar drawn paler); days before the calendar's first are left out. Nine charts in three groups (`CHART_GROUPS`): net worth as stacked coin, goods and property under its own line, coin and loans, goods in store per good (in each good's chart colour), property, income by source, expenses by kind (`_EXPENSE_PARTS`), profit and loss round nought with its average, the townsfolk per class, and happiness per class by the hour. Each has four headline figures over the plot, a range (`RANGES`: Season, Year, All; `GameState.depot_chart_range`, not saved), days summed or closed up into seasons when there are more than the plot has room for (`BAR_PITCH`, `POINT_PITCH`), a legend whose names hide or show their series (`GameState.depot_chart_hidden`, per chart; a total cannot be hidden) and bring it forward on hover, the list's time frame shaded at its right end, and a tooltip of the hovered column's figures. One y-axis only: nothing is drawn on a second scale. Colours with no entity of their own come from `INKS` in that fixed order, checked for colour-blind readers against the parchment. The accounts have a tab per time frame (`PERIOD_DAYS`); a row marked with a lozenge opens its details and turns the charts to the matching one (`ROW_CHARTS`). Hitboxes are filed each frame (`depot_chart_buttons` as `"chart:"`, `"range:"`, `"series:"` plus a name; `depot_buttons` as `"frame:"` plus a name; `depot_plus_rects`; `depot_scroll_rect` for the wheel), cleared by `Game` every frame, and handled by each module's `handle_click`. The plot is drawn into a layer kept until its figures, size or focus change, so a frame of both halves costs about 2.5 ms.

### Merchant Rank

`MerchantRank` (`src/models/merchant_rank.py`, owned by `Game` as `merchant_rank`, saved under `"merchant_rank"`) holds the player's title on the ladder `MERCHANT_RANKS` in `constants.py`, Peddler to Patrician. Each rank asks for four things at once: net wealth (`Depot.net_wealth()`, property included, loans taken off), property value (buildings at their buy price), lifetime trade volume (`Depot.trade_volume()`, goods bought plus sold) and reputation (`Player.reputation`). Rising is checked every game update, paused or not (`check_rise`): the moment all four allow it the player rises to the highest rank they can, and `RankUpWindow` (`src/ui/helper_modules/rank_up_window.py`) announces it on a certificate-like sheet: the numeral in a wreath, the ladder, what it opens, the road to the next rank, a line per rank in `RANK_WORDS` (a rank with none just leaves it out), "Rank Restored" for one held before. It takes no input for `INPUT_DELAY_S`, so a click meant for the market does not close it. Falling is judged at midnight (`daily_check`): when the rank held stops being met, a warning starts `RANK_GRACE_DAYS` of grace, after which they fall back one rank (and get a new grace period if that one is unmet too). The rank shows at the right of the top bar, red while slipping; clicking it, or "Merchant Rank" in the Guildhall's house menu, opens `RankWindow` (`src/ui/helper_modules/rank_window.py`), the whole ladder against what the player has. Rank changes go to the ledger under `RANK`. Rises and warnings wait in `Game._pending_notices`, shown one at a time by `Game._show_next_notice`, which pauses the game and holds them back while a dialog, a minigame or the contract view is open. What a rank opens is in `RANK_UNLOCKS` (rank name per unlock, read with `has_unlocked()`) and follows the *highest* rank ever reached, so it is never taken away; so far `buy_buildings` (Hawker), checked in the buy-building dialog, which is why Hawker asks for no property, and `buy_great_warehouses` (Merchant), the seven Hanseatic warehouses north of town (`Speicher_1`–`7`, 5,000 to 15,000 coins, 1,000 to 2,000 units; three in slots of 100 at 5 to 6 coins a unit, four in slots of 50, which sort goods better, at 8 to 9.5): a warehouse names the unlock it asks for in its Tiled `Buy_unlock` (`Warehouse.buy_unlock`, `buy_buildings` without one). Bonuses that follow the rank held are not decided yet. Reputation comes from gifts (church, town, alms, and goods given to the church for a meal for the poor: `record_gift()` after the donation is booked), from turning down a thanks' gift (`models/thanks.py`, a fixed amount), and from petting a sheep, `SHEEP_PET_REPUTATION` (0.2) the first time each game day (`_pet_sheep` in `figurine_click_menu.py`, `Statistics.last_sheep_pet_day`, saved; it shows as "+0.2" and the laurel rising from the player's head, `on_reputation_gained` in `src/ui/transaction_feedback.py`, a `ReputationPopup` among the coin popups; tested in `tests/ui/test_sheep_petting.py`). A season's gifts together earn `DONATION_REPUTATION_SCALE * ln(1 + given / W)`, W being what the giver was worth before them, so each coin earns less than the last and the rich must give far more; it fades by `REPUTATION_SEASONAL_DECAY` at the start of each season.

"Records" in the Guildhall's house menu opens `RecordsWindow` (`src/ui/helper_modules/records_window.py`), the player's successes, so far the minigames', a tabbed page each, on parchment in a broad frame (`framed_sheet(..., corner_blocks=True, theme=...)` in `tutorial_sheet.py`: double rules round a band of two interlaced waves, meeting in the council's charter's corner blocks), each page in colours of its own (`PageTheme`, `PAGE_THEMES`: the fishing's woad blue, pewter and ripples, the woodhacking's walnut, oak, wood grain and a green laurel; the Gourmet Collection's saffron, honey gold and umber with a linen weave, `GOURMET_PAGE`, its pictures in brass frames), each page drawn once and kept while the window is open. Fishing: the best day's fishing, and a card for every kind of fish but the minnows with its portrait, name, how many were landed, their weight together and the biggest one (`Statistics.fish_tally`, `fishing_records`, filled by `Statistics.record_fish`); a kind not caught yet is grey with a question mark for its name. Woodhacking: the top `WOODHACKING_TOP_SCORES` scores with their calendar dates, hovering one shows its session's best streak, perfect hits (swings perfect on both gauges) and blocks chopped (logs split), and beside them the bests and totals over all sessions (`Statistics.woodhacking_scores`, `woodhacking_bests`, filled by `Statistics.record_woodhacking` when a session is finished; one left early counts for nothing). What was not tracked yet shows as `-`: an older save keeps its high score as an entry with nothing else known, and its bests start with its first new session. A fish's weight follows from its kind and length, `Species.kg(cm)` (`Species.plumpness` × length cubed), and `Fish.kg`; it pays nothing yet, coins still go by length (`fish_coins`). Saves from before the tally count each kind with a record as one fish of that weight.

### Town Council

`Council` (`src/models/council.py`, no pygame; owned by `Game` as `council`, saved under `"council"`; a save without it starts with the data file's council) is a first piece of the roadmap's P6, built ahead of its turn; `docs/council.md` has the design, how it fits P2 to P8, the balance table and the loose ends. Update it when the rules change. `assets/data/council.json` defines the eight offices in three tiers (`Office`: stipend a day, `fee_discount`, `licence_discount`, `standing` (reputation a season), `feud_shield`) and the town's eleven notables (`Notable`: a trade, the good each `likes`, an `integrity`, their `arms`), eight of them in a seat, three without: stand-ins for P5's dynasties. The merchant rank is the title that opens an office (`COUNCIL_TIER_RANKS`, the rank *held*), and a seat may be at most one tier above the one held. The council sits once a season (`session_moment`: its `COUNCIL_SESSION_DAY`th day at `COUNCIL_SESSION_HOUR`; `Council.update(date)`, called every game update, holds the session and returns a `SessionReport`). A name must be down before that day begins (`stand`, for `COUNCIL_FILING_FEE`); the seat is then voted on by the holders of its own tier and the one above (`electorate`; never a candidate, and not the player, who has no vote on the others' seats yet). A voter goes for whom he makes the most of (`_score`): the player by `effective_favour` (the regard their reputation and office earn with everyone, `baseline`, plus what courting him has won, less his grudge), a notable by a fixed liking (`_affinity`), the holder `INCUMBENT_BONUS` ahead, all with `VOTE_NOISE`; a tie leaves the seat with its holder. Favour is courted with gifts of coin (`gift_money`: a season's gifts earn `FAVOUR_GIFT_SCALE` x ln(1 + given / `means`), never above `FAVOUR_GIFT_CEILING`; the `means` are a floor by tier or 2 % of the giver's net wealth, so the rich must give more, as with reputation), with the good he is fond of out of the stock (`gift_goods`, worth `LIKED_GOOD_WORTH` times its price), and a banquet once a season (`host_banquet`); what was won fades by `FAVOUR_DRIFT` a season. Before a vote, at most `PURSES_PER_ELECTION` purses may be offered (`offer_purse`: refused by the upright, with favour and reputation lost, and with `PURSE_TALK_CHANCE` talked of in the hall) and one voter kept from the session (`arrange_delay`: it may fail, and with `DELAY_FOUND` be traced back). Whoever the player beats bears a grudge; from `FEUD_ACTS_FROM` on it is a feud, and each season (`new_season`, which returns the notices to show) he may slander the player, have their stores inspected for a fine, or turn the other notables against them, and he stands against them when their seat is voted on again after `COUNCIL_TERM_SEASONS` (`_call_defence`); grudges fade or are bought off (`make_amends`). The council also goes about its own business (`_decide_others`: the longest-sitting notable confirmed or challenged), so seats change hands without the player. Every draw comes from `Council._rng(tags)`, seeded by the game's seed and what is decided, so nothing of a generator is saved. What an office gives: its stipend each day (`Depot.book_labor_income` under "Council Stipend"), the lower market fee through `Depot.fee_discount` (set by `Game` each update, not saved; `Depot.effective_fee_rate`), the cheaper licences in `ContractOverview`, and reputation each season. Gifts are booked as donations under "Council Gifts" (no reputation for them), fees, purses, banquets, amends and fines as miscellaneous; what happens goes to the ledger under `COUNCIL`.

"Town Council" in the town hall's house menu opens `CouncilWindow` (`src/ui/helper_modules/council_window.py`), a sheet drawn as an official charter (`charter_style.py`: iron-gall ink, sepia rules, dull ochre and an oxblood red instead of the records' gold and red, corner blocks with a quatrefoil instead of the scrolled flourishes; `SessionWindow` uses it too, while the records and how-to pages keep their gold) with three pages, drawn afresh each frame over a sheet made once: the offices as a pyramid of cards (the chosen one set out below, with "Stand for election", "Withdraw your name" or "Lay down the office"), the notables (a list with their favour, and the chosen one's gifts, amends, purse and delay), and the election (the candidates, how each voter leans, in words only, and the council's minutes). What can be clicked is kept in `_hot` as it is drawn (`button_rect(key)` for the tests). A session the player had a part in waits in `Game._pending_notices` like a rise in rank and opens as `SessionWindow` (`session_window.py`): the votes fall one after another under the candidate they went to, then the verdict and what came of it. Nobody has a portrait: `src/ui/heraldry.py` draws each notable's coat of arms (a field colour, one charge of `CHARGES`, a metal; the player's are `PLAYER_ARMS`). `python build_tools/Council_Trial/council_trial.py` plays headless elections over 200 seeds and prints how often a seat is won and what it costs: run it after changing the council's numbers.

### Resting and tiredness

`Player.tiredness` (0 rested to 1 worn out, saved) rises with the game hours the player is up, full after `HOURS_TO_EXHAUSTION` (40), and falls by resting, `FULL_REST_HOURS` (8) clearing any. From `TIRED_FROM` (80 %) on the player is worn out (`src/models/drowsiness.py`, no pygame; tests in `tests/models/test_drowsiness.py`): a penalty from `PENALTY_MIN` (5 %) to `PENALTY_MAX` (25 %) at full tiredness slows the walk (in `MapPlayer.speed_factor` with the weather and a sweet), takes that share off every woodhacking swing's points and off the time a fish holds a taken bait, and shrinks the fishing fight's bar; the map darkens round the player (`src/ui/layout_modules/drowsy_view.py`, drawn by `draw_map_view` after the lightning), the clear oval shrinking from `VIEW_WIDE` to `VIEW_NARROW` of the view, and now and then the eyes fall shut for a second or so, the oval closing to a slit and opening again (`Drowsiness`, owned by `Game` as `drowsiness`, real seconds while the map runs; `BLINKS_PER_MINUTE`, `SHUT_S`); a red circle with a drooping eye (`tired`) among the effect circles names it, and the minigames show a plaque. `Tiredness` (`src/models/rest.py`, no pygame; owned by `Game` as `tiredness`) counts the hours each update (a minigame's jump of the clock counts as hours up), restarted on loading a save. Once the intro is done, Uncle Gared's shop (`intro.SHOP_HOUSE`, `can_rest_at`) has "Rest" in its house menu, which opens `RestWindow` (`src/ui/helper_modules/rest_window.py`), the game paused under it: a 24-hour dial with now at its top and the hours clockwise, its ring coloured by the day ahead's own light (`ambient_light`: night blue with stars and the moon, pale by day with the sun), a gold arc to the hand, and on the slate in the middle how long and until when. The hand starts at the next sunrise (`next_sunrise`, sun hour `SUNRISE_SUN_HOUR`; `default_end`) and moves in `REST_STEP_MINUTES` up to `MAX_REST_HOURS` (24): dragged, clicked to on the ring, the wheel (Shift: an hour), the arrows. "Rest" (Enter) first lets everything behind the window go dark (`DARKEN_SECONDS`), then sets the clock turning: a silver hand sweeps clockwise from now round to the chosen moment in `turn_seconds` (2.5 to 5 s, by the square root of the hours, so a short rest turns slower for its share of the dial; eased; a frame moves it on at most `MAX_FRAME_SECONDS`, so a stutter skips nothing), pausing there `ARRIVED_SECONDS`, the slate showing the time going by and how long is still to come, the tiredness bar emptying and the gold of the rest still ahead shrinking, a clock ticking meanwhile (`clock_ticking.wav`, `CLOCK_SOUND`, looped, louder by `SOUND_GAIN`: it fades in as the dark falls and out over `CLOCK_FADE_OUT_S` from the hand's arrival, or `CLOCK_WAKE_FADE_S` on waking early) (`RestWindow.animate`, called each frame by the main loop for a window that has it; a click or a key wakes at once, at the chosen moment all the same). Then it moves the clock on at a stroke and the window on black dissolves into the game as it now is (`RestWindow.wake`, `Game.fade_in_from`; `Tiredness.rest`, at most one midnight crossed, so each day's work is done once; the weather is advanced by the time rested, since it takes any jump as at most `MAX_STEP_MINUTES`). The inns let rooms too (`src/models/inn_rooms.py`, no pygame): a tavern's house menu has "Book a Room" (`RoomBookingWindow`, `src/ui/helper_modules/room_booking_window.py`), a night (`NIGHT_HOURS`, 24, from the moment it is booked) or a season (`DAYS_PER_SEASON` days) at `ROOM_PRICES` by the tavern's class (10/60, 20/120, 50/300 coins), paid as cost of living; booking again lengthens a held room from its end. The bookings are `Player.rooms` (the tavern's Tiled name to when the room is up, saved in the player's block). While one is held, "Rest in Your Room" (or the booking window's "Rest now") opens the same clock with `until`: the hand stops there (`latest_end(now, until)`, `snap_end`, `default_end`; `can_rest_until` needs a step left), the ring past it is veiled and marked red, and "Until sunrise" becomes "Until checkout" when the sun rises later (tests: `tests/models/test_inn_rooms.py`, `tests/ui/test_room_booking_window.py`). The bottom bar shows the tiredness as a bar beside the population (`_draw_tiredness_panel` in `layout.py`). The player walks slower in bad weather (`Weather.walking_slowdown()`: `WALK_SLOW_RAIN` at full rain, `WALK_SLOW_MUD` on wet ground, `WALK_SLOW_SNOW` in deep snow, added up to at most `WALK_SLOW_MAX`, 15 %) and faster after a sweet: `Game` sets `MapPlayer.speed_factor` from both each update, and a red circle on the map names it (see the Taverns section).

### Taverns

A building with a `Tavern` property in Tiled (`low`, `middle` or `high`, kept as `House.tavern_class`) is a tavern; its house menu has "Daily Menu", which opens `TavernMenuWindow` (`src/ui/helper_modules/tavern_menu_window.py`). The dishes are period ones in `assets/texts/taverns/dishes.csv` (dish, class, course, type, meat, price in coins, description; the menu shows the price; the type, `DISH_TYPES`, is how it is served, `plate`, `bowl` or `drink`, which decides the example its picture is drawn after); `daily_menu()` in `src/models/tavern_menu.py` draws 2 or 3 dishes (`MENU_SIZE`) from the tavern's class, the first a main dish (`HEARTY_COURSES`), the others each from another course, the same all day (seeded by the date and the tavern) and different from tavern to tavern, with no meat on fast days (Fridays and Lent, `calendar.is_fast_day` in `src/sim/calendar.py`). Each dish is a box that orders it on a click (`order_dish`): its price is booked as cost of living and the dish counted in `Statistics.dishes_tried` (saved, by `dish_key`, its name in snake case; the box says whether it was eaten before). A dish with a picture, `assets/pictures/dish_<dish_key>.png` (so far `dish_roast_pigeons.png`), is then shown in `DishServedWindow`, a click going back to the menu. Every dish does something for the player for 6 to 12 hours of game time (`meal_hours`: `MEAL_HOURS_MIN` to `MEAL_HOURS_MAX`, in half hours, mostly by how filling its course is, `COURSE_STAYING`, a main dish the longest and a drink the shortest, then by its price and a little by the dish itself, the same every time; `MealEffect.hours`, a save without it counting as 6) (`src/models/meal_effects.py`, no pygame; `Player.meal`, a `MealEffect`, saved in the player's block): by its course, a main dish with meat gives Strong Hand (that share more points on every woodhacking swing, added to the streak's bonus, `WoodhackingMinigame.strong_hand`), one without, a pottage or a side Well Fed (tiring that much more slowly, `Tiredness.update`), a sweet Light Step (walking that much faster) and a drink Steady Hand (a fish that has taken the bait holds it that much longer, `Hook.hold_extra`, the extra time graded as a late strike); how strong goes by the price on a log scale, `STRENGTH_MIN` (2 %) at `PRICE_FLOOR` to `STRENGTH_MAX` (15 %, the most any effect gives) at `PRICE_CEILING`, so only the high tavern's dearest mains come near it. One meal's effect at a time: a new dish replaces it (its box on the menu says so). The menu's boxes and the served window say what a dish does, the Explore map shows what acts on the player as circles in its top left corner (`src/ui/layout_modules/effect_circles.py`, drawn last by `draw_map_view`, on the map only): a pictogram (`src/ui/effect_pictograms.py`: an axe, a fishhook under its float, a bowl of stew, a winged boot; for the weather a rain cloud, a snowflake or a boot in mud, drawn with pygame's shapes at four times the size and smoothed down) on a parchment disc in a ring, gold for a meal and running out clockwise from the top with its hours, red and whole for the weather; hovering one says what it does, where from and how long it has left, and a click on one does not go through to the map (`GameState.effect_circle_rects`). The minigames show a plaque while one is on. So far there are two: the Grey Griffin Inn on the market square (`middle`) and The Golden Sheaf north of it (`low`). "Gourmet Collection" in the Guildhall's house menu opens `GourmetWindow` (`src/ui/helper_modules/gourmet_window.py`), on the sheet of the guild's records: a tab each for the plates, bowls and drinks (`Dish.type`, `dishes_of`, from the plain tavern's dishes to the fine one's, by course and price), a card per dish with its picture, name and how often it was eaten (`Statistics.dishes_tried`), a click on a tasted one showing its picture large over the collection, dimmed behind it (the tavern's `DishServedWindow`, `GourmetWindow.enlarged`; a click or Escape puts it away); a dish not tasted yet is greyed out with a question mark for its name and only its outline as a flat grey shape, and hovering it tells only where it is served, a tasted one also what it is, its price and what it does. The pictures are large, so each has two small copies made ahead in `assets/pictures/dish_previews/` (`src/ui/dish_previews.py`): `<key>.png`, the picture shrunk to the card (`PREVIEW_SIZE`), and `<key>_silhouette.png`, only its outline in grey (`silhouette`, from `dish_mask`: the pictures have a painted wall and table behind the dish, so the background is what the picture's edge colours reach, the dish's own outline thickened meanwhile, `SILHOUETTE_CLOSE_PX`, so food coloured like the table does not leak, thin bits such as crumbs trimmed, `SILHOUETTE_TRIM_PX`, worked out at twice the size, its edge rounded off and made soft, `SILHOUETTE_ROUND`, `SILHOUETTE_FEATHER`). The game only loads them (`load_preview`); the Sprite Manager makes a dish's pair when it saves its picture (`food_sheets.save_picture`), and `python build_tools/Dish_Previews/make_dish_previews.py` (`--missing`, or dish keys) makes them all; a dish without one shows a drawn outline of a plate, bowl or cup.

### The lost sheep

A first quest (`src/models/lost_sheep.py`, no pygame; owned by `Game` as `lost_sheep`, saved under `"lost_sheep"`; a save without it has not begun it; it happens once a game). The flock grazes in the walled fold south-west of the market (`Sheep_Fold`, a rectangle on `Movements`, its gates `FOLD_GATES`); the black sheep is Flip (`Name` property on his `Sheep` rectangle, `Sheep.name`, shown as his title once the shepherdess has named him). If the player opens a fold gate (`use_gate` tells `LostSheepOnMap.player_opened`) and it still stands open in the evening or night (sun hour from `EVENING_FROM` to `MORNING_FROM`) while they are `AWAY_TILES` from the fold with the fold out of sight, Flip slips out (`check_escape`; an evening the clock jumped over since its last check, as in a rest through the night, counts too, `first_evening`; a gate shut again by anyone undoes it) and grazes on the island between the rivers west of the River Fork, over the West Bridge (`Flip_Island`, a sheep's strip). From the next morning (`missed_on`) the shepherdess keeps the fold instead of her stall (`TraderShepherdess.keeps_fold`, from `LostSheep.on_meadow`; the `StallRota` passes over a trader `kept_away`; she walks from her door through the fold's gate, opening and shutting it, `Trader.passes_gates`, to her round, `Shepherdess_Fold`, and home in the evening by `FOLD_OUT_WINDOW` / `FOLD_IN_WINDOW`; she changes over only while at home or unseen) until the day she has thanked the player. While she has news and is on her round in the fold (not on her way there) a gold "!" bobs over her (`src/ui/layout_modules/quest_marker.py`, drawn after the lighting) and she glows. Her talks are offered as "Do you need help?", and as "About Flip..." once she has named him (`talk_option`); they are `PAGES`, played by `src/ui/helper_modules/lost_sheep_talks.py` (an answer's `does`, `talks.Answer.does`): "Oh no, who would do this?" costs `LIE_REPUTATION` (-3; the farmer saw them), owning up `CONFESS_REPUTATION` (-0.5), not shown beside the answers, only rising in red from the player's head once answered (`on_reputation_lost`). Flip's menu then has "Coax Flip Home": with a Bread one is used up (`Depot.use_goods`, booked as nothing) and he is led on a leash (`src/models/leash.py`: he walks along the player's own trail, `FOLLOW_GAP` behind, put behind them if left past `SNAP_DISTANCE`, as after a load; `Sheep.lead` / `move_led`; no obstacle while led), its rope drawn into the render queue (`leash_view.py`, `rope_points`: sagging by the slack, swaying, taut once a rope's length apart); without bread he gets no heart but shies away along his strip (`Sheep.shy_away`, `SHY_DISTANCE`, only turning his back with no room) and the player says so in their own bubble (`player_says`) and the shepherdess then gives one, once (`BREAD_GIFT`). While he is led the player walks `LEASH_SLOWDOWN` slower (an effect circle, "Leading Flip") and no building's menu opens (`show_house_menu` warns `WARN_BUILDINGS`; gates still work). Inside the fold he is home (`LostSheepOnMap.update`) and walks back to his strip (`Sheep.walk_home`): by day she is there and thanks the player; at night they put him back with the flock themselves and she thanks them the next morning (`THANKS_NIGHT`). Her thanks: `THANKS_GIFT` (3 Wool) or `THANKS_REPUTATION` (1) for turning it down; she keeps the fold to that day's end. What happens goes to the ledger under `QUEST`. `LostSheepOnMap` (`src/models/lost_sheep_map.py`) is the glue to the map, `Game._update_lost_sheep` calls it each update and `step_leash` each frame the map runs.

The fences area (`fences.py`, `fence_sheets.py`, `view_fences.py`, `view_fence.py`, `view_fence_design.py`, `view_fence_answers.py`) makes fences and walls out of straight pieces: a style is `assets/map_sprites/houses/fences/<style>/` with a `fence.json` (material wood, stone or metal, posts every `posts_every` tiles or at the ends only, raster height, description, the lengths wanted, optionally its own draft `colours` and a `plan` of where its pieces go, which the style's screen lays out with the sketches standing in for pieces not drawn yet; a wall with pillars at its ends only has them on its horizontal pieces alone, its vertical ones plain wall running in under the corner pillars, as the old yard's walls do), its pieces `<style>_h<n>.png` (across) and `<style>_v<n>.png` (down the picture, north to south), each saved on its raster at 32 px a tile ((n + 1) x 2 tiles, or 2 x (n + 2)) so pieces laid end to end meet post on post; the game loads one like any building, `File_name` `fences/<style>/<style>_h4.png` on a `Fence_Frontal` point at the raster's bottom-left corner (the tool gives its collision properties). The food area (`food.py`, `view_food.py`) lists the tavern dishes of `dishes.csv` by type (plates, bowls, drinks), each with its picture `dish_<key>.png` or missing, and each type's example, the picture its other dishes are to be drawn after so they look alike (`EXAMPLE_DISHES`, else the type's first dish with a picture: Roast Pigeons for the plates, none yet for bowls and drinks). "Send in browser" (Ctrl+W) sends the chosen dish to the Gemini tab like any sheet, its type's example picture as it is with a prompt asking for the same picture with only the food changed (`food_sheets.py`), "Send ... missing" (Ctrl+Shift+W) every dish of its type without a picture or an answer waiting, one after another; its answers open in `view_food_answers.py`, where accepting one fits it to the example's proportions and size and saves it as the dish's picture, making its previews for the Gourmet Collection with it. "Open image" (or a file dropped on the window) takes a picture already on disk: as an answer to accept when the type has an example, else straight as the dish's picture. The animals area (`animals.py`, `animal_sheets.py`, `view_animals.py`, `view_animal.py`, `view_animal_answers.py`) lists the folders under `figurines/animals/` and adds animals; an animal's frames face left (standing, `move1`–`4`, `eat1`–`2`), accepting one also saves its mirror image as `<animal>_right_<frame>.png`, and the sheep is its pose guide as the chibi is the humans': a frame is drawn on a 2x2 sheet in the sheep's pose, a new animal's standing sprite beside the sheep standing. The crops area (`crops.py`, `view_crops.py`, `view_crop.py`, `view_crop_design.py`, `view_crop_answers.py`) adds crops and makes their growth stages like walk frames: on a crop's screen the stages (added after the chosen one or taken out, with a title, description and height for the prompt), the chosen stage's variants, and the chosen variant growing stage by stage at one scale. Each stage sprite is drawn from a reference sprite and a sketch, like a new plant (`crop_sheets.py`): Enter or a click on its sheet opens the sketch screen, the plants' and buildings' `SketchView` (`view_sprite_design.py`) with the stage's dashed red height line and grey ground line drawn over the red frame as help only, never in the image sent. There the reference is picked, which picks the prompt: another stage of the crop to grow it from (the ripe plant for a smaller one), another variant of the stage for a variation, or, for a crop with no sprite yet, another crop's ripe one for the style (default `Crop.reference_for()`). Each reference keeps its own sketch in `build_tools/output/crops/<crop>/sketches/`; a variant not sketched cannot be sent. It adds people (gender and a name from `medieval_names.py`, or a trade; townsfolk get `npcs/<class>_<name>/` with an `npc.json`) and makes their first front sprite from a description, and can redo the front sprite of anyone who has one. It makes NPC walk frames (`<prefix>_<direction>_move<n>.png`) and standing sprites from the base chibi's strips in `base_Chibi/`, and the player's frames: his run is `player_<direction>_move<n>.png` (in the game he only runs), his walk `player_<direction>_walk<n>.png`, not loaded by the game yet. Per frame it builds a 2x2 sheet with a see-through ghost of the pose in the target cell (with "Head: Locked" the figure's own head is put in place of the ghost's, where its standing sprite faces the frame's way; "Sheet: Two cells, red ghost" (L) sends only the figure beside the pose as a red ghost instead, with its own prompt; "Model figure on top" keeps the grid but puts a figure whose walk is done in its top row, standing and in the same frame, instead of the mannequin, the grey mannequin ghost still in the red frame (Bartholomew at first, `Settings.model_figure`; "Model:" or K picks another, `model_picker.py`; a frame the model lacks falls back to the grid), and each answer records its layout so `extraction.py` splits it right), handed to Gemini either through the API or by copy and paste via the web view (`win_clipboard.py`), or with "Send in browser" (Ctrl+W): `web_bridge.py` serves it on 127.0.0.1:47613 to the userscript `gemini_bridge.user.js` (Violentmonkey/Tampermonkey, installed from that address), which opens a new chat in the Gemini tab (opened in the Firefox profile `FIREFOX_PROFILE`, "ProjectTrader", where the userscript is installed) and sends image and prompt (setting the thinking level to High is switched off, `CHOOSE_MODEL` in the userscript, since Gemini's model menu dropped it; the code is kept for when it comes back), then waits (up to ten minutes) for the answer's image and clicks its "Download full size"; the tool picks the new file out of the Downloads folder, books it on the sheet it was sent for as if opened, and plays a small chime made from sine waves (`chime.py`) ("Send missing in browser", Ctrl+Shift+W, sends every frame of the direction not done yet that way, one after another, and plays a full chime when all are through, stopping at a sheet that fails); a sheet that does not come through plays a falling chime; its selectors are what to fix when Gemini's page changes. Every answer is kept in `build_tools/output/<npc>/` and listed in a `review.json` (`pose_review.py`), to be accepted into the sprite folder or marked as not good enough; `extraction.py` cuts the sprite out and scales it. "Even out colours" (`even_colours.py`, needs numpy) pulls a direction's frames onto its standing sprite's colours, material by material, so the walk does not flicker; the old frames are backed up and one click undoes it. The plants and the buildings areas (Tab goes round all three) show the map sprites, by kind (a building some object on `Map1.tmx` names in its `File_name` is labelled "in game"). Both are a `Domain` of `sprite_library.py` (`plants.py`, `buildings.py`: kinds, proposals, prompt, Tiled hints); which kind each sprite is lives in `plant_catalog.json` / `building_catalog.json` (right-click to change), and the small plants, which exist only inside `non_collision_deco.png`, are cut out of it on the fly. Clicking a sprite starts a new one with it as the example: the user sketches the shape in the red frame beside it (under it, for a wide one) in flat colours (brush, straight-line and fill tools; the colours used last are quick picks, kept per domain in `recent_colours.json`), picks type and an optional subcategory, and the split image goes to Gemini like the humans' sheets. Accepting saves a single sprite (`trees/Tree_<n>.png`, `houses/House_<n>.png`, ...) and stamps it into the first free tile-aligned place of `Trees.png`, `non_collision_deco.png` or `Houses.png` for Tiled, after backing the PNG up (the `.xcf` sources are not updated); when that is full, into the next of its series, `Houses_2.png`, `Houses_3.png` ..., starting a new empty one as big as the first when all are full, with its own `.tsx` beside the map, added to `Map1.tmx` as a tileset (`Atlas.series`, `start_overflow` in `sprite_library.py`; the game loads every tileset of the map, so commit them with it); the status line gives the Tiled properties for its object (a tree's stem, a building's size and collision box, a bridge's `Bridges` rectangle and deck guess). A kind may add rules to the prompt (`Kind.prompt_notes`, as the bridges do). Floor plates (the market square's paving, `floor_plates/Floor_<n>.png`) are a buildings kind whose collection is `assets/tiles/ground_tiles.png`: a new one is stamped there and painted onto `Ground_High` from the `ground_tiles` tileset; the single sprite is only the tool's example and is not loaded by the game. A bridge's near railing is cut out as its `_front.png` by `bridge_front.py`: `prepare` writes the bridge on white plus a prompt asking Gemini to paint all else magenta, `cut` takes the answer as a mask over the bridge's own pixels. The main script only holds the window, main loop and shared state; each screen is a `View` subclass (`view_*.py`) and the non-UI parts live in their own modules — its docstring maps them. Prompts for hand use live in `sprite_prompts/`.
